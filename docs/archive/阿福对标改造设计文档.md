## 0. 「世界顶级」的定义与总原则

阿福的领先由三部分构成：**问诊产品结构、多模态与档案纵深、平台生态**（30 万真人医生、好大夫、挂号购药医保、设备厂商）。生态部分是平台资源，不是问诊能力，桌面单机产品结构性不具备——本设计对生态差距给替代设计或明确不做，不假装能复制。

诚信的既有优势不动摇：鉴别驱动的问诊内核（8 通路 25 假设）、确定性红旗层（recall 1.000 / 误报 0）、结论单确定性拼装 + 禁用语 lint、发布门与评测语料体系。这些是阿福公开资料中**没有对应披露**的可验证性资产。对标的方向是补齐阿福已证实做得好的部分（表达、多模态、档案、诊后），同时避开它被用户批评的坑（轻症一律劝医、互动机械、越问越焦虑、跨对话遗忘）。

**总原则（全阶段适用）：**

1. **K1–K8 内核契约不动**；问诊决策路径保持确定性 + 模型信封的既有架构，新能力一律以旁路/产出层形态接入，不进决策关键路径。
2. **临床内容纪律不变**：一切新医学文案（科室映射、报告分级阈值、皮肤方向、self_care 补齐）均为 engineering-v1，登记进《待临床评审清单》，患者可见性默认 shadow，临床签核后开启。
3. **患者可见即可核**：任何进入问诊上下文的档案数据、任何 AI 产出（识别/解读/草稿），患者都能看到来源与原文，不做静默注入、不做不可核的断言。沿用既有治理：识别值须患者确认才可引用；结论单命中禁用语整单作废。
4. **每阶段独立过门**：pytest 全绿 + 发布门 PASS + 新增评测语料 + live-eval 回归（问诊体感不退化）后才合入 main。

## 2. 差距分级

- **A 已达标/领先（不投入）**：问诊追问内核与鉴别覆盖、红旗确定性与否定语义、结论单结构完整性（处置/方向/缺口/自我护理/安全网/展望，阿福公开口径只有三要素）、评测与发布门、逐字证据校验。
- **B 工程可补（本设计范围）**：G1–G11 全部。
- **C 生态型（替代或不做）**：真人医生网络与医生复核 → 替代为「就诊摘要」（阶段四）把患者高质量地送到线下医生面前；挂号/购药/医保支付 → 不做；设备直连同步 → 替代为拍照读数 + 手工录入（已有管线）；AI 开处方 → 监管禁止，不做；名医 AI 分身 → 不做（权责风险，阿福自身亦被质疑）。

## 3. 阶段一（P1）：结论表达与分级呈现

目标：把结论单从「字段陈列」升级为阿福式「先安抚定性 → 讲清原理 → 大白话说严重程度」的叙事结构，并补齐分级视觉与科室管线。全部为产出层改造，不动问诊决策。

### 3.1 结论叙事层（新增 `narrative` 字段）

- composer 新增确定性拼装的三段叙事（模板 + 事实引用，**不引入模型自由文本**）：
  1. **定性段**：由 disposition + tier 选模板，引用患者主诉原话与关键事实，先给「这是什么量级的问题」的定性（如「这类情况多数不凶险，但有一项需要当面排除」）；
  2. **原理段**：由 directions 的 support_quotes / against 证据与 gaps 拼装「为什么这么判断、还缺什么」；
  3. **程度段**：disposition 的口语版 + 时间窗 + return_now_if 首条，给「到底多严重、多久内行动」。
- 三段全部过既有 banned-phrase lint（沿用 compose 末尾的整单校验）；模板资产进 `content/` 并登记临床评审清单（engineering-v1）。
- `spoken_close_line` 同步升级为叙事版三段的压缩口播，保持「处置 + 警示 + 120」既有要素。
- 前端：结论卡顶部渲染 narrative 三段（定性段为视觉首行），其后仍是既有分节（结构化信息不丢）。

### 3.2 分级视觉语言

- disposition 三档色标：self_care=绿、routine_visit=黄、urgent_today=红（沿用现有 CSS 变量体系，含深色模式与色盲友好校验——不单独依赖颜色，配图标/文字标）。
- 急诊关闭（无结论单）的 emergency_explanation 同步获得红色警示样式对齐。

### 3.3 outlook 补齐（G3）

- self_care.json 13 个空 course 组补齐 engineering-v1 文案（按通路病程常识：一

- 把「不支持证据」呈现从 resp_breathing 单例泛化为规则：direction 的首个 evidence_against 若来自患者明确否认的事实，生成「你否认了 X，这一点不支持它」句式（X 取事实的患者向标签）；事实标签表复用 handoff LABELS 并补齐（与阶段四 6.2 共用一张表，避免双份维护）。

### 3.6 对话内共情层（G4）

- `agent_prompt.txt` 增加共情表达段（短、可执行）：每轮先一句确认/承接（引用患者刚说的内容）、提问前给一句「为什么问这个」、患者表达担忧时先回应担忧再继续流程；**明令不放松的纪律**：收尾结论仍由宿主代行（prompt :38 不变）、证据与不确定性纪律不变、禁用语不变。

## 4. 阶段二（P2）：健康档案纵深

目标：档案从「血糖 + 图片转录库」升级为「基线 + 多指标 + 家庭」的纵向健康档案，并治理良好地进入问诊。分三个子阶段，每个子阶段独立过门。

### 4.1 P2a 基线档案

- `patient_profiles` 扩展基线（SCHEMA_VERSION 1 → 2，正向迁移）：出生年、性别、身高、体重、慢病清单（结构化多值）、过敏史（药物/食物/其他）、长期用药（药名 + 用途，自由文本受长度约束）、手术/住院史摘要。全部患者自填、可改、带 updated_at；不从问诊事实自动回写（避免未确认信息污染基线，如需回写须走患者确认，与 shareable 治理同构）。
- 前端：健康档案视图新增「基线信息」区（表单 + 展示），records 徽标与时间线不变。

### 4.2 P2b 测量泛化

- `add_measurement` 从血糖硬编码泛化为 kind 注册表：blood_glucose（既有）、blood_pressure（收缩/舒张双值）、temperature、weight、blood_oxygen；每 kind 定义单位集、合理范围（超限只警告不拒绝、标记 clarity）、趋势统计口径。复用 glucose 的单位归一与收据模式；`glucose_trend` 泛化为按 kind 的 trend 查询，档案页趋势区按 kind 分组渲染。
- 影像转录的 document_number 观测在患者确认时可「另存为测量」（血压计/体温计照片 → 结构化测量），打通拍照读数链路（阿福拍读数场景的等价实现）。

### 4.3 P2c 档案进问诊（自动注入，决策点 D5）

- **基线投影**：新会话开启时把基线档案（慢病/过敏/长期用药/年龄性别）以 `profile_baseline` 投影进**双引擎**上下文（补齐 G8 parity：确定性引擎与结论单同步消费 report_items 与 baseline）；投影字段白名单、长度上限，沿用 prior_case 的投影纪律（只给与问诊相关的摘要，不给全量档案）。
- **患者可见与可控**：问诊页顶部明示「本次问诊参考了你的健康档案（慢病/过敏/用药）」+ 一键关闭本次引用；关闭状态记事件。注入内容在事实面板中以「来自档案」来源标记呈现，与本次问诊事实区分（不写进 CaseState.facts，只进上下文投影——避免档案值被当作本轮证据污染校验链）。
- **已确认测量引用**：最近的已确认测量（如近 7 天血压/血糖趋势摘要）以数值 + 时间 + 来源随 baseline 一并投影；趋势只给描述统计（min/max/均值/最近值），不给判断。
- 结论单可在 gaps/self_care 拼装时引用 baseline（如过敏史影响 avoid 项时以模板提示「你档案里记有 X 过敏，涉及用药请先核对」——仅模板提示，不做药物判断）。

### 4.4 P2d 家庭成员（决策点 D1）

- 推翻 single_patient_only：`patient_profiles` 多行启用，新增成员管理（添加/改名/归档）；成员基线结构与本人相同（4.1）；儿童成员增加出生年月（月龄计算供问诊年龄题使用）。
- 问诊绑定：consult_for 确认问诊对象后，若对象匹配某成员档案，会话绑定 member_id；attach 门控由「consult_for=self」泛化为「条目所属成员 == 本次问诊对象」；baseline 投影取绑定成员的档案。
- 本人档案与成员档案在 UI 与数据上严格分区；既有单人数据零迁移成本（默认档案即本人）。

**P2 验收**：迁移测试（v1 库升级后数据完整）；测量注册表单测 + 趋势断言；双引擎 baseline 投影 parity 测试（同一档案两引擎上下文等价）；家庭成员的 attach 门控正反例；live-eval 中档案引用不干扰问诊主流程。

## 5. 阶段三（P3）：多模态解读层

目标：在既有「忠实转录」之上补「解读」——这是阿福多模态的核心价值（报告红黄蓝绿灯 + 行动清单）。解读层与转录层严格分离：转录只管事实，解读是独立的、可关的产出层。

### 5.1 P3a 报告解读（先行）

- 启用闲置的 `analysis_runs` 表：解读运行记录（entry_id、输入观测修订 id 集合、产出 JSON、模型/版本、状态），输入**只取患者已确认的观测**（未确认值不进解读，避免在错误转录上叠加解读错误）。
- 产出合同 `report-interpretation/v1`：逐项 {observation_ref, 通俗名称, 结果复述（值+单位）, 分级 ∈ 绿/黄/红/无法判断， 大白话解释， 行动建议 ∈ 观察/复查/尽快就诊/急诊} + 整体小结 + 固定声明（「由 AI 生成，未经医生审核；分级依据为工程版参考区间」）。
- **分级依据**：新建 `content/reference_ranges.json`（engineering-v1，登记临床评审 C13）：常见检验项的参考区间与三档阈值；**无参考区间的项一律「无法判断」，只解释不分级**（fail-closed）。模型只负责把转录值对齐到内容项与生成大白话解释（草稿性质），分级由确定性规则按阈值计算，不由模型决定。
- 患者确认的参考范围缺口：转录合同里 reference_range 恒为空的现状（attach 投影）由本内容资产补齐来源。
- 治理：解读产出过 banned-phrase + 剂量/处方 lint（复用 education 的双路 lint 模式）；解读可带入问诊（扩展 attach：解读摘要作为 report_items 的注释来源，仍以已确认观测值为准）。
- 前端：条目详情新增「解读」节（分级色点 + 大白话 + 行动清单），与转录观测分区呈现；档案时间线条目标记「已解读」。

### 5.2 P3b 皮肤拍照（决策点 D3，默认缓行）

- 识别合同扩展 `skin-observation/v1`：只产出**形态描述**（部位/形态/颜色/分布的结构化描述）+ 紧迫度信号（是否命中既有红旗表的皮肤相关触发，如快速扩散的红肿伴发热——走既有确定性红旗层，不新造判断）。
- 「可能方向」如需给出，复用 differentials 的 skin 通路三假设与 certainty 措辞，且**默认 shadow**（登记 C14），与问诊内皮肤通路同口径，不做独立的「50 类识别」宣称。
- 皮肤图同样走归档 → 确认 → 引用的治理链；形态描述经患者确认后可带入问诊作为 skin_details 的证据候选（仍须问诊内校验，不直接落事实）。

### 5.3 P3c 识别异步化

- 识别改异步：POST recognitions 立即返回 202 + run_id，entry 状态机（recognizing）已有，前端轮询 entry 状态刷新；45s 同步阻塞消除。演示后端（demo）保持 offline 语义不变。

**P3 验收**：解读合同与分级规则单测（含无区间必「无法判断」的 fail-closed 用例）；解读语料（构造 ≥20 份合成报告条目：正常/单项异常/多项异常/含未确认值/含无区间项）断言分级与 lint；视觉走查解读节；皮肤分支如启用，shadow 语料先行。

## 6. 阶段四（P4）：预问诊交接与随访触达

目标：把「交接单」升级为阿福医生端预问诊的患者侧等价物——一份医生 30 秒能看完的就诊摘要；随访从「页面里等你来看」升级为桌面端可达的提醒。

### 6.1 就诊摘要 v2（G6）

- `build_handoff` 升级 patient-handoff/v2：并入结论单核心区（disposition 文案、directions（可见时）、self_care 要点、return_now_if、随访计划）+ 档案基线区（绑定成员的慢病/过敏/用药，来自 P2）+ 既有事实/报告项区；limitations 更新为预问诊口径。
- LABELS 补齐全部事实键（sex、pregnancy_status、recent_exposures、reported_temperature、symptom_location 等），与 3.5 共用同一张标签表；新增漂移守卫测试：domain 注册的每个 fact key 必须有患者向标签。
- 呈现：新增打印友好的独立摘要页（浏览器打印 CSS，一页 A4 目标）+ 导出 .md/.txt 文件下载（复用 handoffLines 拼装）；对话框保留。

### 6.2 随访触达（G11，决策点 D4）

- 桌面端本地通知：Electron 主进程在应用运行时检查 due（复用 workspace.follow_ups 的 due 判定），到期未记录结局的 plan 触发系统通知（点击直达随访列表）；Web 版保留页面内通知并增加「到期中心」徽标聚合。应用未运行时不承诺送达（明示边界，不引入后台服务）。
- due 粒度细化：`content/followup_windows.json`（engineering-v1）按通路组给常规随访窗（24/48/72 之外允许 5–7 天档），urgent 维持 24h；build_follow_up_plan 查表，plan 结构不变。
- 草稿交互：维持「只起草不发送」边界；用户可一键复制草稿（与 handoff 复制同路径）。

### 6.3 用药提醒

- 基于档案长期用药（P2a）+ 本次问诊 medications_taken，生成本地提醒计划（时间点由患者设定，系统只按时提醒「该吃 X 了」，不提供剂量建议、不判断相互作用）；提醒与随访共用 6.2 的通知通道与到期中心。

**P4 验收**：handoff v2 结构测试 + 标签漂移守卫；摘要页打印走查（一页、字段齐全）；通知在桌面端实测触发一次；due 查表语料断言。

## 7. 横切事项

- **评测与门**：每阶段新增语料必须进发布门且带最小样本断言（沿用本轮 all_cases_pass 纪律）；live-eval 每阶段至少一轮 9 例回归 + 一轮新能力专项；任何阶段不得使红旗 recall、结论 agreement 等既有门项退化。
- **隐私与数据**：档案/图片继续本地存储（现有权限位与 sha256 不变）；家庭成员数据不出本机；baseline 注入的可见性与关闭权（4.3）是硬要求；影像识别继续走用户配置的模型后端，设置页明示「图片将发送到你配置的模型服务识别」。
- **语音输入**（阿福有、本设计暂缓）：桌面 Chromium 的 Web Speech 依赖外部服务且 Electron 内可用性不稳，单列预研，不进 P1–P4 承诺；长辈友好已部分具备（字号三档），P1 视觉改造时顺带核查大字档下结论卡可读性。
- **不做清单**：真人医生网络/复核、挂号购药医保、设备直连、AI 处方与剂量、名医分身、跨设备云同步。理由：生态与监管边界，非工程能力问题。
