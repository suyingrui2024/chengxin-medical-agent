# 架构分层规则

> 状态：已生效（CI 强制）
> 权威实现：`scripts/lint/import_rules.py`（规则细节以脚本 docstring 为准）
> 规模约束：`scripts/lint/module_size.py`（单文件 ≤ 1200 行）

---

## 1. 三层结构

分层不由目录嵌套表达，而是由门禁显式声明：

| 层 | 成员 | 职责 |
|---|---|---|
| **capability** | `extensions/`、`kg/`、`facts/` | 公式/量表/血糖引擎、知识图谱、共享事实表。被广泛复用，必须对业务无知 |
| **feature** | `consultation/`（含 `consultation/agent/` 自适应引擎）、`conclusion/`、`execution/`、`patient_records/`、`subagents/` | 五条临床工作流 |
| **kernel** | `core/`、`guards/`、`dialogue/`、`clinical/`、`reports/`、`review/`、`infra/`、`shared_types/` | 共享内核：所有层都用的词汇、守卫、交互、推理与产出（见 §9） |
| **app** | `server/` | HTTP 表面 + 组合根（`runtime`、`workspace`），压在所有层之上 |

顶层只留 `__init__.py`、`cli.py`、`desktop_service.py` —— 即包入口与两个进程入口。

**依赖只能向下。** 能力层不认识功能层；功能包之间互不认识；共享内核不认识功能层；只有进程入口（`cli`、`desktop_service`）可以 import `server`。

## 2. 为什么这样切

能力层若依赖功能层，就无法脱离某条工作流复用或测试。两个功能包若互相 import，就无法独立修改——改 A 必须回归 B。

这正是 `module_size.py` 管不到的那类腐化：文件可以很小，同时把依赖伸到毫不相干的包里。

## 3. 六条规则

| 规则 | 内容 | 当前状态 |
|---|---|---|
| R1 | 能力包不得依赖功能包 | 0 违规 |
| R2 | 功能包之间不得互相依赖 | **0 处**（见 §4） |
| R3 | 仅入口可依赖 `server` | 0 违规 |
| R4 | 禁止循环依赖 | 0 个环（已全部打破） |
| R5 | 顶层扁平模块数不得增长 | **2**（仅 `cli`、`desktop_service`） |
| R6 | 共享内核不得依赖功能包 | **0 处**（见 §4） |

## 4. 已知债务（冻结而非豁免）

**R2 硬耦合 0 处**——功能包之间不再有模块级互相依赖。基线已清空：功能包之间再出现跨包硬依赖就是新违规，直接失败。

**已解除（6 处）**：
- `subagents.* → conclusion`（5 处）：原本为共享 `BANNED_PHRASES`、`GAP_IMPACTS`、`MEASUREMENT_FACTS` 三张事实表。已抬进零依赖的 `facts` 包。
- `agent._preamble → consultation`（1 处）：这不是工作流之间的耦合——`AdaptiveConsultationEngine` 是 `ConsultationEngine` 的**子类**，两个包本来就是同一个引擎拆成两半（确定性内核 + 自适应扩展）。`agent/` 已并入 `consultation/agent/`，跨包边变成包内边。

解除方式是把共享部分抬进能力/内核包，不是放宽规则。

**R6 内核→功能硬耦合 0 处**——共享内核不再依赖任何功能包。基线已清空：内核→功能边再出现就是新违规，直接失败。

**连延迟导入也是 0**：此前 `closing` 曾在函数内导入 `conclusion` 的窗口措辞与口头结语。`closing.py` 本身就是收尾渲染逻辑（443 行），已搬进 `consultation/closing.py`——`consultation/_preamble.py` 原先只是 `from .. import closing` 再转发，属层级错位。现在内核里没有任何一行代码提到功能包。

**契约类型下沉**：`UserInput`、`StaleActionError`、`SubjectBoundaryError`、`ConsultationBusyError` 原本在 `consultation/types.py`，迫使内核模块（`location_revisions`、`observations`、`task_conversation`）延迟导入功能包。现已下沉到内核包 `shared_types/`；`consultation/types.py` 保留为再导出，8 个 `from .types import *` 的模块无需改动。`observations` 的「是否自适应引擎」判断改用内核的 `ModelBackedEngine` 标记基类，不再 `isinstance` 到 `agent` 包。

**已解除（8 处）**：
- `hypothesis_ranking`、`question_ordering`、`out_of_pathway` 原本只为拿一个谓词（`chief_matches_pathway`）和一张表（`PRIOR_RANK`）而依赖 `conclusion`——谓词已下沉到内核的 `reasoning`（它本来就拥有通路语义与内容加载），表已下沉到 `facts`。
- `recognition_jobs` 驱动 `patient_records` 的存储，本就是病历功能，已搬进 `patient_records/` 包。
- `runtime`、`workspace` 是组合根（组装 consultation、agent、backends、triage 等功能包），与 `server/` 角色相同，已搬进 `server/`。
- `closing` 是收尾渲染逻辑，已搬进 `consultation/`。

顶层模块数随之 65 → 64 → 62 → 61。

**R4 循环依赖 0 个（已全部打破）**：原 5 个环——`conclusion` 内部 5 模块、`execution` 内部 4 模块、`consultation_subject ↔ domain`、`extensions.formulas ↔ formulas_extra`，以及跨 8 模块的大环——均已通过抽取低层共享模块（`formulas_core`、`execution/paths`、`conclusion/assets`）和最后一处内核↔能力延迟绑定（`knowledge → extensions.builtin` 下沉到函数内）清除。`CYCLE_BASELINE` 现已清空：图里再出现的任何环都是新违规，直接失败，不再容忍。

**4 处函数内延迟导入**（`consultation.agent.run`、`consultation.closing`、`consultation.closing_flow`、`consultation.emergency`）保留为刻意破环的写法，只告警不失败。循环检测只在模块级边上做，因此这些延迟导入不会被误判为环。

## 5. 违规了怎么办

```bash
npm run lint:structure     # 本地跑三个门禁（文件规模、依赖方向、大文件基线）
```

- **模块级跨包导入**：把共享部分移到能力包，或反转依赖方向（调用方传值进来）
- **循环依赖**：反转一条边——把值作为参数传入，或在函数内导入
- **不要**往 `EDGE_BASELINE` / `CYCLE_BASELINE` 加新条目。基线是还债清单，不是许可清单。

环被打破后门禁会提示收紧基线（`R4 baselined cycle is gone / shrank`），照着删即可。

## 6. 新代码该放哪

按顺序问四个问题：

1. **只被一条工作流用** → 放进那条工作流的包（`consultation/`（含 `consultation/agent/`）、`conclusion/`、`execution/`、`patient_records/`、`subagents/`）。
2. **被多条工作流用，但只是数据/词表** → 放进零依赖的能力包（`facts/` 这类，或 `extensions/`）。**不要**为了几个常量去依赖别人的功能包。
3. **所有层都要用的词汇/原语** → 放进内核的某个包，**按 §9 的表选**（词汇进 `core/`，校验进 `guards/`，交互进 `dialogue/`，推理进 `clinical/`，产出进 `reports/`，审计进 `review/`，基础设施进 `infra/`）。
4. **只被进程入口用** → `server/`。

**不要**新开顶层扁平模块——R5 会直接 fail（上限 2，只剩两个进程入口）。要加内核代码，加到 §9 对应的包里。

## 7. 依赖速查表

| 从 ↓ / 到 → | capability | feature | kernel | app |
|---|---|---|---|---|
| **capability** | ✅ | ❌ R1 | ✅ | ❌ R1 |
| **feature** | ✅ | ⚠️ 同包 ✅ / 跨包 ❌ R2 | ✅ | ❌ R3 |
| **kernel** | ✅ | ❌ R6 | ✅ | ❌ R3 |
| **app** | ✅ | ✅ | ✅ | ✅ |
| **入口**（`cli` / `desktop_service`） | ✅ | ✅ | ✅ | ✅ |

读法：格子 ✅ = 允许，❌ = 门禁会 fail。模块级违规 = fail，函数内延迟导入 = 只告警。

## 8. 已接受的设计（不是债务）

**`conclusion/` 保持独立功能包，不并入 `consultation/`。**

数据：2,442 行、8 个模块，src 侧**只有 3 个引用方**（`consultation/closing`、`consultation/closing_flow`、`consultation/emergency`），全在收尾路径。所以它看起来像"收尾流程的一部分"，但它**不是** `agent` 那种情况：

| | `agent`（已合并） | `conclusion`（保持独立） |
|---|---|---|
| 关系 | `AdaptiveConsultationEngine` **继承** `ConsultationEngine` | 被收尾流程**调用** |
| 能否独立存在 | 不能——是子类，没有基类就不成立 | 能——契约是 `CaseState` → sheet |
| 能否独立测试 | 不能 | 能，不需要引擎 |
| 合并代价 | 只是移动文件 | 把 2,442 行塞进已 6,800 行的包 |

它的窄接口（`CaseState` → 结论单）是资产，不是偶然。所以**保留**，代价是 4 条延迟导入告警中的 3 条（`closing` / `closing_flow` / `emergency` → `conclusion`）会长期存在。

这 3 条告警是**已接受的设计**，不是待还的债：不要为了把它们消掉而合并包。判定标准很简单——**"能否脱离对方独立存在"**：不能（继承）就合并，能（调用）就保留并接受告警。

**第 4 条告警同理**：`consultation.agent.run → subagents`。自适应引擎在执行阶段派生子代理，而 `subagents` 有自己的生命周期、存储与调度，不依附于 consultation——所以保留，接受这一条延迟导入告警。

## 9. 内核的七个包（找东西看这张表）

| 包 | 装什么 | 成员 |
|---|---|---|
| `core/` | **共享词汇与底层原语**。所有层都要用的类型、事件、文本匹配、状态与呈现 | `domain` `events` `text_match` `phase_graph` `measurement_kinds` `state_transitions` `turn_context` `presentation` `decision_wait` `worry` |
| `guards/` | **安全与证据校验**。决定什么能断言、什么必须扣住 | `assertion_evidence` `direction_guards` `red_flags` `baseline_projection` `self_checks` |
| `dialogue/` | **回合级用户交互**。任务、定位、观测、提问、就诊对象 | `task_intents` `task_interactions` `task_conversation` `location_answers` `location_revisions` `observations` `adaptive_questions` `consultation_subject` |
| `clinical/` | **临床推理与知识** | `reasoning` `knowledge` `interpreter` `hypothesis_ranking` `question_ordering` `out_of_pathway` `reasoner` `planner` `triage` `triage_review` `followups` |
| `reports/` | **对外产出**。报告、教育、桥接、交接、测量报告、计算 | `report_drafts` `report_interpretation` `publication` `education` `bridging` `handoff` `measurement_reports` `patient_calculations` `medication_reminders` `calculation_followup` |
| `review/` | **事后复核与发布核算** | `background_review` `background_review_evaluation` `audit_recording` `release_evaluation` `flywheel` |
| `infra/` | **基础设施**。后端、进程、平台、配置、插件、会话、影像、工具模式 | `backends` `processes` `windows_process` `platform_fs` `env_config` `plugins` `web_tools` `session_store` `medical_images` `agent_tools` |

另有 `shared_types/`：跨层契约类型（`UserInput`、三个异常、`ModelBackedEngine` 标记）。

**这七个包都是 kernel 层**：它们之间可以互相 import（R6 只禁止内核→功能），功能层与能力层也可以 import 它们。所以分组只是**归类**，没有引入新的层级约束。

分组依据是**职责**而不是依赖：这 59 个模块本来就大多是叶子（61 个里 29 个出度为 0），搬动不改变依赖图，只是让人能按名字找到东西。

`docs/` 下写于分组之前的设计文档仍保留旧的 `src/medagent/xxx.py` 路径（那记录的是当时的设计决定）。读者找文件请查 [模块路径变更对照](模块路径变更对照.md)。
