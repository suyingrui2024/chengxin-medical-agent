# 执行能力对照评测

2026 年 10 月 16 日建立。原套件 `paired-execution-benchmark/v1` 使用合成项目；第 5 节新增 `paired-public-dev-execution/v1`，使用真实公开仓库的开发任务。两者用来发现执行适配层造成的能力损失，不用于证明医疗有效性或泛化后的全面优势。

## 1. 独立路径与公平条件

产品路径使用 `ExecutionManager → execution-worker → 官方 DSH SDK`。基线路径由独立的 `scripts/execution_baseline.mjs` 直接创建官方 `DeepSeekHarness`，不经过产品管理器、事件投影、控制插件或产品运行工作进程。两条路径均固定 DSH `0.2.0-rc.2` 和同一实际模型。

两边读取相同初始项目，用户任务和后续任务逐字相同。使用同一 bubblewrap 文件挂载策略、Node/Python 解释器、依赖、外网代理、8192 token 单次输出上限和默认推理配置。官方工具、子智能体深度、搜索提供商配置保持一致。文件隔离本身也用于基线，因此结果比较的是相同约束下的官方 SDK，而非无限制运行用户整台主机的 DSH。

每个任务第一回合最多 24 次请求，接续最多 8 次；辅助检索和子任务同样计费计数。两边经过同一个独立评测网关，转发前预留并持久记录请求；中断留下的未确认请求也保守计入额度。每个完整配对预留 64 次额度，不在最后只缩短第二条路径的预算。顺序由记录在报告中的固定随机种子决定，重复运行使用新工作区。

产品仍保留其自身 persona、动态共享预算提示和委托建议；SDK 基线保留官方默认 persona。这些差异是被评估的产品行为，不能声称两边的完整系统提示逐字相同。两个适配器均关闭日志上传、插件清单上传及自动重试，并以外层文件命名空间负责隔离。基线未使用产品的私有取消插件；本套件只比较正常任务与接续，取消/后台生命周期继续由原生验收独立覆盖。

## 2. 冻结项目与检查器

| 项目 | 用户目标 | 隐藏检查 |
| --- | --- | --- |
| `precision-repair` | 修复单位模块和 CLI，补测试，保留已有接口与测试 | 正常/长精度/极小输入、调用方低精度与上下文不变、非法输入、真实 CLI、后续产物 |
| `csv-feature` | 增加分组聚合模块并修改 CLI | 分组顺序、精确 min/max、总和及均值舍入、空输入、非有限和无效行、CLI 与后续文件 |
| `delegated-review` | 修复金额计算并委托独立子智能体实际复核 | 仅对最终总和舍入、高精度、输入拒绝、官方子会话启动、复核文件、后续结果 |

金额和单位仅是非临床合成代码任务，不把自由生成代码用于患者建议。要求保留的已有测试与固定标识文件必须逐字不变，不能通过删改测试获得通过。

项目、任务、接续提示和检查脚本在第一条 API 请求前计算哈希；运行时与评测脚本同时快照。候选执行环境不挂载 `scripts`，看不到隐藏检查器。两条路径关闭后，由宿主选定检查脚本，在新的同策略命名空间中执行；候选不能在检查期间继续修改文件或读取检查进程。

`tests/test_execution_benchmark.py` 先验证三个检查器均拒绝已知错误种子、接受独立正确参考实现，再破坏接续文件确认它们仍拒绝错误产物。另一项本地真实 SDK 检查验证基线确实调用终端、修改文件、保留进程并继续会话；网关检查覆盖鉴权、单回合/总额度、输出限制和不记录真实密钥。三个测试不调用外部模型。

## 3. 指标与判定

单次通过需要同时满足：两个回合真实完成、同进程接续、额度未超、上游无错误、保护文件未改、必要源码实际改变、独立产物检查通过；要求子智能体的任务还需官方子会话通知。程序退出码零、模型最终回复和子智能体认可都不是单独的通过条件。

报告保存每次运行结果、逐项检查、事件、产物哈希、模型请求数和执行耗时；配对统计区分两边都通过、仅产品通过、仅基线通过和两边都失败。不完整配对不能混入胜负统计。请求是实际转发尝试计数，不能直接换算成已结算费用；未实现统一 token/金额核算时不报告虚构成本。

首次运行因基线使用相对挂载路径启动失败，已中断并保留请求账本，不能计作有效对照。修复把工作区与状态目录解析成绝对路径，并用相对路径实参的本地 SDK 检查补回归。有效对照结果以实际归档为准；少数项目和单次成功不足以证明普遍不劣于 DSH。

## 4. 复现

目前已完成首轮与优化后两次重复。首轮产品 2/3、基线 1/3；优化后产品 6/6、基线 1/6，共 165 次预留转发请求。任务和检查哈希一致，原始失败、产物及源码快照全部保存。完整表格和证据见 [实际配对结果](缓存优化与真实模型评测.md#v091独立dsh对照与截断恢复)。这些仍只是三个自建项目，不是一般能力或临床结果的统计证明。

```bash
# 冻结任务清单预览，不读取密钥或调用模型
PYTHONPATH=src python3 scripts/benchmark_execution.py --output /tmp/unused-report.json

# 检查器和 SDK 驱动的本地正反验证，不调用外部模型
RUN_DSH_EXECUTION=1 PYTHONPATH=src python3 -m unittest discover \
  -s tests -p test_execution_benchmark.py -v

# 显式真实模型配对；读取根目录 .env，用新输出路径
PYTHONPATH=src python3 scripts/benchmark_execution.py --live \
  --repetitions 2 --max-total-calls 192 \
  --output .runtime/benchmarks/new-round/report.json
```

累计额度覆盖输出父目录内请求账本，包含保守预留的中断请求。未完成计划的报告会说明剩余额度不足；不得仅展示通过的任务或覆盖旧结果。评测与运行日志只使用合成数据；发布归档前扫描真实密钥。此套件尚未覆盖长期上下文压缩、大型仓库、项目依赖安装、多模态、系统级故障和完整的联网对照；需要逐步增加由独立人员设计的任务及重复样本。

## 5. 公开仓库 DEV 任务补充

当前版本的复杂任务可靠性仍不足。固定 DSH `0.2.0-rc.2`、`deepseek-flash`、相同源码与逐字相同的用户任务，每个任务各重复两次：严格任务判定产品 **2/8**、独立 SDK **1/8**。恢复冻结测试、配置和依赖后，仅检查候选实现的补充结果为 **4/8**、**3/8**。补充检查没有改变原始失败判定。这些结果不能支持“整体达到或超过 DSH”。

[SWE-bench Lite 官方说明](https://www.swebench.com/lite.html)提供 300 个 TEST 和 23 个 DEV 实例。本轮在模型运行前人工选择 DEV 中四个任务，涉及三个仓库；未使用 TEST 集调优。数据文件、源码归档、缺失依赖 wheel 均固定 SHA-256。选择受本机资源和可运行环境限制，既非随机样本，也非未知保留集；公开历史任务还存在预训练污染可能。

使用 `/usr/bin/python3`、系统 pytest 和现有 bubblewrap；没有采用官方 Docker harness，因此**不是官方 SWE-bench 分数**。预检先证明原始实现的 6 项 FAIL_TO_PASS 全部失败、231 项 PASS_TO_PASS 全部通过，参考修复后 237 项全部通过。八个历史参数化测试名存在截断，清单保存唯一的完整名称映射；断言与测试数量保持不变。首次适配失败报告也已归档。

| 任务 | 产品严格通过 | SDK 严格通过 | 产品实现检查 | SDK 实现检查 |
| --- | --- | --- | --- | --- |
| pydicom-1139：PersonName 迭代 | 0/2 | 0/2 | 0/2 | 0/2 |
| pydicom-1694：JSON 异常处理 | 0/2 | 1/2 | 2/2 | 2/2 |
| marshmallow-1359：嵌套字段格式 | 1/2 | 0/2 | 1/2 | 1/2 |
| astroid-1268：Unknown 节点展示 | 1/2 | 0/2 | 1/2 | 0/2 |
| 合计 | **2/8** | **1/8** | **4/8** | **3/8** |

严格判定同时要求任务回合完成、调用额度未超、提供商无错误、已有测试/配置/依赖逐字未改、实现实际改变，以及全部上游指定检查通过。补充审计从原始源码重新构建，仅覆盖候选包内 Python 实现，再执行冻结上游测试；它用于区分代码正确性和联合评分，不替代原始指标。

复核发现一项评测描述局限：用户任务写“保留已有测试……可以新建普通回归测试文件”，没有明确说明“不能在已有文件追加测试”。严格检查却采用文件级 SHA-256；观察到的三次测试文件改变主要是添加回归用例，不能直接据此断言模型违背了明确的用户要求。此前将其称作“约束违规”过强，现改为“未满足严格字节保护门”。原始评分和失败数据保持原样，代码正确性结果单独报告。后续实验应在模型运行前明确文件级保护契约、允许的新文件范围和实际检查标准，并记录提示差异；不能将澄清后的提升全部归因于智能体本身。

实际计数：产品 113 次请求、SDK 176 次，共 **289 次**；产品回合完成 8/8，SDK 2/8。配对严格结果为产品单独通过 2 组、SDK 单独通过 1 组、两者均失败 5 组。产品额外注册两个医疗工具；实际共有 25 个官方工具，完整清单在报告内。persona、预算提示和注册医疗工具差异均属于本次产品条件，不宣称系统提示或完整工具集完全相同。

首份报告在 210 次请求后停止：256 次上限只余 46，无法预留下一配对双方各 24 次。追加入口校验已有运行时、任务和评测源码未变，保留首份报告，在同一账本下提高累计上限至 384，只补齐原计划缺少的两组配对。最终 16 次运行全部完成。该上限是请求预留边界，不能直接换算成货币成本。

主要失败证据与下一步：

- PersonName 的候选实现均未通过上游 `next()` 行为检查；不能只用自行选择的预期值验证自己。
- Unknown 节点的首次候选返回空串或简化占位符，未满足上游表示约定；需要检查相邻 API 与对象约定。
- 产品两次改变已有 `test_json.py`，SDK 一次；即使补充实现检查通过，原始严格字节保护检查仍为失败。由于任务描述存在上述歧义，这项计数不能直接用作用户约束遵守能力的比较。
- 扩展测试触发外部数据下载和长等待；部分 SDK 运行在实现已正确时仍耗尽额度。后续应优化工具等待与收尾，并保留真实测试退出码。

## 6. v0.9.6 执行反馈与可视化迭代

本轮交付两类可重复验证的改进：前台命令默认等待 10 秒、单次最多 30 秒后交还同一后台任务；Bash 默认启用 `pipefail`，使摘要管道保留失败退出码。执行界面将调用与返回合并成一张状态卡，显示前台、后台非零退出和等待状态，标题栏集中显示模型请求数；长输出保留头尾，详情可展开。状态来自 SDK 返回标记的投影，任务正确性仍由独立检查判定，不能作为患者事实或临床结论。

实现继承官方 `SandboxBashExecutor`，沿用 SDK 文件工具、job runtime、子智能体和取消机制。首次覆盖配置因直接更改已有插件名称被官方机制跳过，本地回归捕获了实际退出码缺失；修正为禁用旧实例、插入派生执行器。`dsh:check` 增加完整 profile 的实际配置核对，真实 SDK 测试验证退出码 7 和约 30 秒移交后的原任务产物。原生测试另验证后台 `completed, exit code: 9` 显示为非零退出，并保留长输出的末尾标记。

**真实模型正确性尚未提高。** 在同一四个 DEV 任务上各重复两次，恢复冻结测试后的实现检查为产品 **4/8**、SDK **4/8**；上一版分别为 4/8、3/8。PersonName 迭代与 Unknown 表示仍未通过指定兼容检查。部分 issue 没有完整说明上游测试要求的精确行为，这也是极小人工样本的局限；全部原始失败继续保留，判定标准保持不变。

| --- | --- | --- |
| 独立实现检查 | **4/8** | **4/8** |
| 模型回合正常完成 | 8/8 | 1/8 |
| 逐字文件保护检查 | 7/8 | 6/8 |
| 原始联合评分 | 3/8 | 0/8 |

文件保护检查继续使用第 5 节存在歧义的旧任务措辞，原始联合评分不能解释为纯编码能力优势。请求数与耗时是观测值，包含模型采样差异、外部测试数据下载及服务波动；基线实现保持不变但耗时也明显变化，因此不能据此将差异全部归因于等待策略。后续应先明确文件级契约，并扩大信息充分、可复现的未知任务覆盖。

同一配置模型名称 `deepseek-flash`、同一初始源码、逐字相同的用户提示、每臂 24 次额度、180 秒任务时限及 8192 token 单次输出上限。产品的前台等待、默认 `pipefail`、persona、共享预算提示和两个医疗工具属于被评估的差异；SDK 路径保持上游 shell 默认配置，差异在报告 `shell_conditions` 内明确记录。任务、代码和评测源码在第一条请求前冻结，本轮 90 个记录文件在结束时保持一致。共 **308 次请求**，低于预先设定的 384 次上限，16 次运行全部完成。这是已知开发任务的迭代，不是官方 SWE-bench 成绩、未知保留集或临床验证。

工程验收：154 项后端、21 组界面、源码与打包版各 8 组原生检查通过；63 个运行文件与打包版一致，544 个已安装依赖版本与源锁文件一致。打包器对开发脚本、开发依赖清单和顶层锁文件的清理单独记录，不以这些元数据差异误判运行代码不一致。当前桌面启动入口指向 `Chengxin-0.9.6-linux-x64`。

## 7. v0.9.7 结构化反馈验收

本轮改善运行观察与展示，没有再次宣称编码准确率提高。0.9.6 的公开 DEV 产品/SDK 实现检查 4/8、4/8 保持为历史结果；尚未完成信息充分的独立保留集，整体达到 DSH 仍未得到证明。

工具状态改为读取官方 `tools/result` 的规范 `value`，与终端文字分开。前台进程采用实际退出码和信号；后台进程由 job ID 关联，读取独立生产者结果；子会话保留自己的身份。近期观察可跨应用恢复，旧记录缺失状态时不补造。界面保留紧凑卡片，并在滚动区外显示本轮异常入口，点击定位首项详情。详见 [结构化观察协议与边界](通用执行底座与能力评测设计.md#9-v097-结构化运行观察)。

本地后端 156 项、界面 21 组、源码与打包版各 8 组原生检查、桥接与状态 6 项全部通过。后台准备测试最初使用了错误的 starting 状态假设，源码核对后改为固定 SDK 实际发出的 running；准备阶段、唤醒和取消行为均由真实 SDK 检查，没有据此宣称发现并修复了已复现的 starting 缺陷。Node 检查在受限环境下曾只输出文件级结果，最终以允许测试子进程运行后输出的 6 项实际断言为验收依据。

真实模型定向实验在请求前冻结 69 个运行与评测文件，结束时哈希全部一致。总上限 24 次，实际 **7 次请求，全部 HTTP 200**；11 项检查通过，包含误导文字但实际退出 0、真实退出 7、后台退出 9、子会话实际执行、结果文件与无凭据离线恢复。检查器根据 SDK 规范结果与实际调用关联判定，没有使用模型最终总结作为唯一证据。子任务也实际执行了相同的误导打印命令。

该实验是一个明确指定工具步骤的合成验收，适合验证反馈通道，不足以证明自主规划、一般编码、多模态、医疗建议或临床质量。观察通道与智能体共享运行环境，不能当作对抗同用户权限恶意代码的不可伪造证据；宿主注册医疗计算仍使用独立回执。
