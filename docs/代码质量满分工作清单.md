| 批 | 包 | 函数数 | 模块数 | 预计 |

## 3. Phase R2：两个贴边模块的处置（架构 9 → 10）

**现状**：`execution/session.py` **1190 行**、`consultation/agent/execute.py` **1149 行**，
上限 1200。再有一次普通改动就会撞线，而"贴线运行"意味着下一次改动被迫仓促拆分。

**动作**：先做职责清点，再决定拆不拆——和 `_validate_report` 的教训一致，
拆错比不拆更糟。

1. **清点**：列出两个模块的每个符号、它的使用者数量、它依赖的模块。
   `execute.py` 的七个 `_tool_*` 方法已经是清晰的家族；`session.py` 的
   artifact 投影 / store 协作 / 恢复逻辑是三个候选切面。
2. **判据**：只有当"一个切面能不回头地搬走"（搬走后原文件不需要再 import 它）
   才拆。切面之间共享状态的不拆。
3. **拆**：每个模块最多拆出一到两个文件，名字按职责
   （候选：`execution/session_resume.py`、`consultation/agent/proposals.py`）。
4. **收紧门禁**：`module_size.py` 上限从 1200 降到 **1000**，基线同步重算。

**验收**：
- [ ] 两个模块低于 1000 行，或清点表写明"每一段为什么必须留在这里"
- [ ] `module_size` 上限 1000，全绿
- [ ] subtests 恒为 11958；浏览器全绿

**风险**：中。`session.py` 是浏览器路径，拆完必须跑全量浏览器验收。
**预计**：1 天。

## 4. Phase R3：43 个长函数逐条判定（可读性收尾）

**现状**：43 个 >100 行的函数在尺寸基线里。上一份方案已经把承诺从"持续下降"
改成"只降不升 + 季度复查 + 随改动消解"，但**季度复查没有开始过**。

**动作**：一次做完首轮复查——不是拆，是**逐条判定并留档**：

1. 为每个函数填一行判定表：`函数 | 职责数 | 判定 | 理由`。
2. **只拆判定为"有第二个职责"的**。预期多数判定是"单一职责"：
   协议解析、数据装配、文件系统状态机。
3. 判定表落在 `docs/长函数判定表.md`，成为季度复查的起点——
   下次复查只看"这次改动碰过哪些"。

**验收**：
- [ ] 43 条全部有判定与理由
- [ ] 拆分的（预计 0–5 个）各自一个提交，subtests 恒定
- [ ] 基线数字只降不升

**预计**：判定半天；拆分按判定结果另计。

## 5. Phase R4：CI 覆盖拉满（纪律 9.5 → 10）

**现状**：

- `main-quality.yml`：patient-safety + browser-suite 两个 job，PR 与 push 触发 ✓

- **macOS 完全没有 CI**——而开发机就是 macOS；README 的 macOS 行还写着
  "尚无 CI 验收"
- `README.md` 第 23 行的声明需要随 CI 现状更新

**动作**：

1. **macOS job**（新 workflow 或并入 main-quality）：Python 全量 + 前端单测 +
   全部结构门禁 + `npm run test:ui -- appearance`（一个 spec 文件冒烟，
   不跑 52 个——macOS runner 贵，且浏览器逻辑与平台无关）。
2. **Windows 进 PR 路径**：加 `schedule`（每日一次）+ `pull_request` 里
   paths-filter 只在动到 `src/`、`desktop/`、打包脚本时触发——
   全量 Windows 验收 40+ 分钟，不适合每个 PR。
3. **README 更新**：macOS 行改写为实际状态；补一句 CI 拓扑说明
   （ubuntu 全量 + Windows 定时 + macOS 冒烟）。

**验收**：
- [ ] 三个平台都有 CI 且触发条件明确
- [ ] README 与实际一致
- [ ] 三条 workflow 在干净 checkout 上各通过一次

**风险**：低。macOS runner 的成本是需要你确认的取舍（见 §8）。
**预计**：半天。

## 6. Phase R5：患者数据出域（合规——**这是清单里最重的一项**）

**现状**：项目把病历、照片、语音送进模型（DSH 官方 SDK 或 compatible 后端），
而 `src/medagent/` 里 `脱敏 / deidentif / anonymi / redact / 隐私`
**零命中**，docs 里没有一篇隐私或数据流文档。
对一个医疗项目，这比任何可读性欠账都重。

**这一项需要你先回答三个事实问题**（答完我才能写）：

1. `dsh` 与 `compatible` 两种后端下，患者数据分别发到哪里？（本地进程？公司内网？第三方云？）
2. 出域前有没有任何处理（脱敏、截断、字段过滤），还是原文直接发？
3. 患者数据在本地落盘的边界是什么（`MEDAGENT_PATIENT_DATA_DIR` 之外还有哪里）？

**拿到答案后的动作**：

1. **写 `docs/数据出域与隐私.md`**：一张数据流表——
   数据类型（主诉/照片/语音/计算输入）× 后端（demo/compatible/dsh）×
   出域与否 × 落盘位置 × 保留期限。
2. **补代码**（按事实决定）：至少要有 `scrub` 同级的守卫——
   事件与日志里禁止出现患者自由文本，写一个扫描门禁。
3. **README 补一节**"数据去了哪里"——患者和审计者最先问的就是这个。

**验收**：
- [ ] 数据流文档覆盖每一种数据类型与每一种后端
- [ ] 门禁：`agent.*` 事件 payload 与日志行不含患者自由文本（用测试夹具的真实会话验证）
- [ ] README 有数据去向一节

**预计**：文档 3h + 门禁 3h；**前置是你回答三个事实问题**。
