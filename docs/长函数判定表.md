## R2 附：两个贴边模块的职责清点（2026-11-03）

[满分工作清单](代码质量满分工作清单.md) Phase R2 的清点结果。两个模块
（`execution/session.py` 逻辑 ~1190 行、`consultation/agent/execute.py` ~1150 行）
按"切面能不回头地搬走"的判据逐一检查后，**判定：本轮不拆，留在基线里**，
理由记录如下——下次改动触碰它们时按此重新评估。

### `execution/session.py` —— 执行会话的状态机

| 组成 | 行数 | 为什么留 |
|---|---|---|
| `_read` | 212 | worker 事件流的唯一消费点；每个事件分支都写 `self` 的状态并调用 `persist()`——搬走它就要把整个可变状态一起搬走 |
| `__init__` | 142 | 装配：目录身份、状态目录、store/lease、能力绑定——全是 `self` 的字段 |
| `artifact_overview` / `snapshot` / `changes` | 180 | 三个读路径，都从同一组 `self` 字段推导，且都要先拿 `self.lock` |
| `persist` | 93 | 写回 store，读写 `self.turns` 与 `self.settings` |
| `_start` / `_terminate` / `_run` | 160 | worker 进程生命周期，操作 `self.process`/`self.reader_thread` |

**共同的耦合点是 `self` 本身**：12 个方法全部读写同一个可变状态对象，
拆出的任何文件都要么带回整个状态、要么把状态改成参数在两边传来传去——
后者是 `_validate_report` 已经证明过的参数爆炸。真正可行的拆法是先把
`_read` 的事件分发改成 handler 表（行为不变的重构），那是一次独立提交。

### `consultation/agent/execute.py` —— 模型工具的执行层

| 组成 | 行数 | 为什么留 |
|---|---|---|
| `_tool_ask_patient` | 121 | 自检/澄清/追问三入口共享同一"先收自检"判定 |
| `_tool_spawn_subagent` | 115 | spawn 的模式判定与 shadow 记录 |
| `_tool_review_summary` | 101 | 摘要核对与 abstain 理由 |
| 其余 `_tool_*`（8 个） | 40–85 | 每个工具一个方法，已按工具命名 |

**这其实是七个 mixin 方法的集合，命名已经按工具分开**；它们共享的是
`state`、`turn_id` 和"提议必须可追溯到患者原话"的判定结构。拆成七个
单方法 mixin 只会把一个执行层变成七个互相 import 的文件。

### 重新评估的触发条件

- `_read` 的事件分发被改动（先做 handler 表重构，再谈拆分）；
- 任一模块因真实改动超过 1200 逻辑行；
- 或者有人需要为其中一个写第二份同类工具（届时先抽共同判定结构）。

## 复查方法（下次季度复查照此执行）

1. 用 `module_size.py`/`function_size.py` 同款 AST 口径列出当轮 >100 行函数。
2. 只复查**上次判定之后被改动过**的（`git log -- <file>` 一眼可查）。
3. 每条填：职责数、判定、一句理由。判定"有两个职责"的当场拆，单独提交。
4. 本表随判定更新；基线数字只降不升。
