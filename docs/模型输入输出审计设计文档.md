# 模型输入输出审计设计文档

> 版本：v1.0（2026-10-24）；状态：设计待采纳，未实施。
> 起因：用户要求对智能体中每一个模型的输入和输出做完整检查——像模拟 API
> 调用一样逐个跑一遍，看哪里可以优化。此前只有局部检查（live-eval 正确性、
> 红旗召回、发布门语料），没有全量审计；按通路裁剪提示词前缀曾明确记为
> deferred，本设计把它排进来。
> 约束：不换模型、不动 K1–K8 内核契约、不改临床内容、不把审计结论当成
> 临床签核（见 §6）。审计只改“怎么问模型、怎么收模型答案”，不改问诊
> 决策规则本身。

## 0. 现状一句话

诚信的模型调用面其实很小，但最重的一处被低估了：**自适应问诊决策是
唯一的高频调用点**，且每轮自纠最多发 6 次请求、每次都重发约 25.6K 字符
的静态前缀；其他调用点（子智能体、后台复核、视觉识别）都是低频、
有预算上限的单次或有界多步调用。审计的性价比排序就按这个来。

均为仓库实测或代码级上限；量不到的写“待审计实测”，不估算。

### 1.3 明确不是模型调用点（审计不计入，避免范围膨胀）

- 确定性引擎：`src/medagent/consultation.py` 全文 0 处 backend 引用，
  `runtime.py:59` 在 demo 模式下直接构造 `ConsultationEngine`——零模型调用。
- 结论拼装（`conclusion.py`）、报告分级（`report_interpretation.py`）、
  随访计划（`followups.py`）、交接单（`handoff.py`）、联网检索与延伸阅读
  （`web_tools.py`、`education.py`）：均为确定性代码或确定性 HTTP，
  不调模型。随访草稿由 B 的 followup_batch kind 生成，不另计调用点。
- live-eval 驱动器里的患者子智能体是测试 harness，不属于产品调用面。

### 1.4 最重的三处（按输入规模 × 调用频率排序）

1. **A 自适应决策**：25,569 字符前缀 × 每轮最多 6 次请求，且每次
   都重发前缀 + 全上下文。这是全系统模型成本的主体，也是优化回报
   最大的地方。
2. **B evidence_lookup 分支**：最多 6 步 ×（1K 提示词 + 病例投影 +
   每条 ≤1200 字符的内容摘录 + 多步回喂），且 spawn 总信封 48000 token
   是硬上限不是实测值。
3. **F DSH 决策**：单次成本未知（内部提示词不透明），且 55s 超时窗口
   最长；只能做信封级黑盒审计，不能做段落级优化。

## 2. 审计方法：离线模拟回放

核心思想：**先录制、再回放、最后才动提示词**。审计本身不依赖真实
API key 也能跑通；需要真实模型时只做小样本对照，不把全量审计押在
线上调用上。

### 2.1 输入 fixture 的录制与构造（无 key 可跑的关键）

1. **录制层（新增一个包装后端，不改产品代码路径）**：实现一个
   `RecordingBackend`，实现 `DecisionBackend` 协议，内部委托给真实后端
   或 ScriptBackend，**每次 decide 前把 messages 原样写盘**（JSON 文件，
   按调用点/轮次/会话编号）。注意：现有 `model.requested` 事件只存
   message_chars 与 sha256、不存原文，因此**不能从事件日志反推 fixture**，
   必须在调用处录制。录制只在审计模式下开启，默认关闭。
2. **Fixture 来源（按优先级）**：
   - 黄金会话：live-eval 9 例的真实会话轨迹（run4/run5 口径）重放，
     覆盖 8 通路；每例每轮的 messages 即为 A 的 fixture。
   - 合成会话：用 demo/确定性引擎 + ScriptBackend 构造边界会话
     （空病例、满事实 27 键、超长证据引文、20 条 report_items、
     transcript 满 16 条），用于测上下文增长的上界。
   - 子智能体 fixture：复用现有语料（subagent 24 例）+ 构造 scope
     边界（fact_keys 为空、hypotheses 为空、transcript none/
     evidence_only/recent_window 三档）。
   - 视觉 fixture：已确认观测对应的图片样本 + unclear/unreadable
     样本（≥20 张，含模糊、裁切、多数值同页）。
   - 后台复核 fixture：10 个已关闭会话的快照。
3. **隐私纪律**：fixture 只用合成数据与已脱敏的黄金会话；不得把真实
   患者图片或原话写进仓库 fixture；图片 fixture 用公开样例或程序
   生成的模拟报告图。

### 2.2 逐项度量（每个调用点、每类 fixture 都要出的表）

- 输入规模：system 字符数、user 字符数、总字符数；**token 数必须用
  部署模型的真实 tokenizer 实测**（字符数只作相对比较，不换算成 token）。
- 输出规模：输出字符数、token 数、信封字段数。
- 耗时与重试：单次耗时、重试触发率（按原因分：空内容/429/5xx/
  超时/网络）、自纠步数分布（A：1–6 步各占多少）、子智能体步数分布。
- Schema 健康度：parse/validate 失败率、回喂修复成功率、修复后仍
  失败率、第二意见 tendency 枚举失败率、视觉合同拒收率。
- 校验损耗：record_facts 逐条通过率/拒绝原因分布；子智能体 findings
  丢弃率（按 kind、按原因：无引文/引文不符/禁用语/剂量模式）。
- 缓存效率：Compatible 后端的 prompt_cache_hit 率（前缀复用是否真实
  生效；若命中率长期为 0，前缀瘦身的收益计算方式要变）。
- 上下文增长曲线：A 的 user 消息字符数随轮次的变化（事实数、
  transcript 条数、report_items 条数三个自变量分别回归），确认增长
  是线性还是被 16/20/3 三个上限截断。

### 2.3 “死重量”的判定标准（必须同时满足，缺一不可）

一段提示词或一个输出字段，只有同时满足以下三条才可认定为死重量：

1. **消费点为零**：grep 全仓，模型输出的该字段没有任何产品代码读取
   （或提示词段落对应的工具/事实在全部黄金会话中从未被触发）。
2. **消融无损**：删除该段落/字段后，在 §5 的门禁语料上重跑，
   正确性指标（红旗召回、结论处置、live-eval 对照）零变化，
   且无新增失败类别。
3. **样本充分**：消融对照样本达到 §5 的最低样本数，单例通过不算数。

反例：question_catalog 看似与 fact_schema 重复，但 ask_question 的
候选 ID 依赖它——消费点不为零，不能仅凭“长得像”删除。任何删除都
必须先过消融，不是先删再测。

### 2.4 模拟回放的执行方式

- **离线回放（默认）**：fixture + ScriptBackend（脚本化输出）跑
  校验管线：验证 schema、证据校验、预算、重试逻辑是否与线上一致。
  产出度量表，不花 token。
- **小样本线上对照（需 key 时）**：每类 fixture 抽 ≤5 条走真实后端，
  只验证离线结论（token 数、cache 命中、失败率）是否与线上一致；
  线上与离线分歧超过阈值时，以线上为准并修正度量方法。
- **消融实验**：每次只删/改一处，跑 §5 门禁；多处改动不得打包验证，
  否则无法归因。

## 3. 优化方向分类

### 3.1 提示词瘦身

- 静态前缀：agent_prompt.txt（10,193 字符）与静态目录 JSON
  （15,337 字符）分段消融；优先验证 fact_schema 与 question_catalog
  的重复度、self_check_catalog 与 available_capabilities 在无自检/
  无能力会话中是否可省略。
- 按通路裁剪（deferred 事项，本设计排入 §5 阶段二）：静态目录只
  含主诉触发通路相关的问题与假设，跨通路问题按需后补；必须证明
  裁剪不改变候选问题集合（与全量前缀的候选集逐轮对比）。
- 上下文压缩：facts 的 evidence 原文是否可截断（逐字校验依赖它，
  截断即破坏校验——需先证明校验可改用证据哈希/引用）；transcript
  16 条与 report_items 20 条上限是否可随轮次递减；earlier_source_turns
  是否与 transcript 重复。
- 验收标准：前缀字符数下降 ≥20% 且 §5 门禁零退化；或任一单项
  删除通过 §2.3 三条标准。

### 3.2 输出信封精简

- record_facts 的 correction 重提是否可合并为单条；ask_patient 的
  options 上限 8 个是否常被打满（未打满则上限不是成本项）；子智能体
  conclusion 1000 字上限的实际分布（若中位数远低于上限，上限不是
  问题，findings 条数才是）。
- 验收标准：输出 token 中位数下降可度量，且 schema 失败率不上升。

### 3.3 失败与重试收敛

- A 的 6 步自纠：统计步数分布与每步的失败原因；若某类失败（如
  证据格式）占主导，修提示词措辞或放宽校验二选一，不得只加重试。
- Compatible 的有界重试：统计重试触发率；空内容重试若高频，考虑
  换 response_format 约束或前置长度检查。
- 子智能体回喂修复：统计每 kind 的修复成功率；修复成功率 <50%
  的错误类型应改为事前约束（提示词中明示）而非事后回喂。
- 视觉识别：单次失败即整体失败，评估“失败图片自动降级为 unclear
  候选”与“一次重试”的收益（重试必须有独立预算，不无限重试）。
- 验收标准：任一失败类别的重复发生率下降 ≥50%，且总调用次数不增加。

### 3.4 缓存与复用可能

- 前缀复用：若 cache_hit 率已高，前缀瘦身的边际收益主要是输出
  侧与长会话侧，不必为省输入 token 而牺牲可读性；若命中率为 0，
  先查传输层（消息序列化是否逐轮变化破坏前缀稳定性）再谈瘦身。
- 自纠步复用：同一轮内多次 decide 是否可合并为单次多工具输出
  （需改信封结构，属架构改动，列为远期项，不在本审计内实施）。
- 视觉识别：同一图片重复识别是否可按 sha256 缓存结果（图片已按
  sha256 归档，缓存键现成）。
- 验收标准：cache_hit 率可度量地提升，或证明已达上限。

## 4. 分阶段实施顺序

- **阶段一：录制与度量（只观测，不改提示词）**。产出：§1 表格的
  实测版（token 数、耗时、失败率、增长曲线）+ 调用点覆盖率 100%
  的 fixture 集。验收：每个调用点都有 fixture 与度量表。
- **阶段二：消融与死重量清单**。按 §2.3 逐段消融，产出死重量清单
  （段落/字段、证据、消融结果）。验收：每项删除都有消融对照，
  无“凭感觉删”的条目。
- **阶段三：实施优化（分批，每批一类）**。先 A 前缀与上下文，
  再 B excerpts 与回喂，再 D 视觉重试与缓存；每批独立过 §5 门禁。
  验收：每批都有优化前后度量对比。
- **阶段四：回归与归档**。全量 pytest + 发布门 + live-eval 9 例对照
  + 视觉走查；审计报告写入仓库（度量表与消融结果），供下次审计
  对照。

## 5. 验收门

- 覆盖率：6 个调用点（A–F）全部有 fixture 与度量表，缺一即未完成。
- 最低样本数：A ≥30 轮（覆盖 9 例 live-eval 病例 + 边界合成会话）；
  B 每 kind ≥5 例；D ≥20 张图片；C ≥10 个快照；E/F 以 A/B 的线上
  对照样本为准（每类 ≤5 条）。
- 正确性不退化（优化后必须全过）：红旗召回 1.000、结论语料 108 例
  disposition 1.000、发布门 PASS、live-eval 9 例 risk 与处置级别与
  优化前对照一致（窗口变化须能用随访查表/unknown 封顶解释）。
- 成本可度量：优化前后同一 fixture 集的输入 token、输出 token、
  调用次数、耗时四项对比表缺一不可；只报字符数不算数。

## 6. 明确不做清单

- 不换模型、不改模型供应商与部署配置（thinking/reasoning_effort
  的对比只作为审计度量，不作为默认配置变更）。
- 不动 K1–K8 内核契约：证据逐字校验、record_facts 写入上限、
  红旗短路、子智能体盲化与逐字校验管线均不放宽。
- 不改临床内容：问题目录、鉴别假设、自护文案、参考区间、随访窗
  的数值与措辞均不在审计改动范围内（改动须走临床评审）。
- 不把审计结论当成临床签核：审计只回答“输入输出是否浪费”，
  不回答“医学内容是否正确”。
- 不在仓库 fixture 中存放真实患者原话与图片；不把录制开关默认
  打开；不把 DSH 内部提示词的猜测写成结论（黑盒部分只报信封级
  度量）。
- 不做全量线上重跑：审计默认离线，线上只做小样本对照。
