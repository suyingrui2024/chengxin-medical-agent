### 0.1 一处口径变更（2026-11-03，Phase A 执行中发现）

补文档会让函数变长——`correct_fact` 加了 17 行 docstring 后从 133 行变成 150 行，
当场撞上 `function_size.py` 的基线。**两个门禁会互相打架**：一个要求写清楚，一个按文本长度
判定复杂度。

改的是后者的口径：**尺寸门禁现在不计 docstring**（只减 docstring 本身，不减普通注释）。
一个函数的规模是它的逻辑，不是关于它的散文。

重算后超标函数从 126 降到 **116**——其中 10 个原本只是被 docstring 撑过了线。
这 10 个是真实的改进，不是账面游戏。

## 2. 为什么是这四件事，而不是继续拆长函数

**拆长函数的边际收益已经低于成本。** 剩下的 >100 行的 47 个里，最重的几个是
`compose_conclusion`(297，数据装配)、`capture`(295，文件系统状态机)、`_read`(212，
协议解析)、`_run_spawn`(243，派发与超时)。它们长是因为事情本身长，拆开只会把参数
从一个函数搬到另一个函数——`_validate_report` 那次已经验证过：拆完之后最大的子函数
仍有 88 行，而参数从 5 个涨到 13 个。

**文档是唯一能一次改善 242 个函数的手段。** 35% 的覆盖率意味着一个新人打开
`_run`、`_context`、`_tool_spawn_subagent` 这类函数，看到的是代码而不是意图。补文档
不改一行行为，风险接近零，收益覆盖三倍于拆函数的函数数量。

**每一项都有门禁，所以成果不会漂回去。** 这是与"再优化一轮"最重要的区别。

## 3. Phase A：给关键函数补上"为什么"（优先做）

### 3.1 范围与分批

**只补核心三包 + 门禁拦住新增**，不做全仓 242 个。

| 批次 | 范围 | ≥25 行且无 docstring | 预计 |
|---|---|---|---|
| A1 | `consultation/agent/` 全部 | 14 | 1.5 小时 |
| A2 | `consultation/` 顶层 | ~20 | 2 小时 |
| A3 | `conclusion/` + `reports/` + `clinical/` | ~18 | 1.5 小时 |
| — | `execution/` `server/` `dialogue/` `infra/` 等 | ~190 | **不排期**，改到那个文件时顺手补 |

### 3.2 写什么

不是"复述代码"，是三句：

```python
def _deliver(self, state: CaseState, reply: AgentReply, turn_id: str) -> AgentReply:
    """Publish one reply and remember it as the session's latest.

    The reply is stored in ``_latest_replies`` so that a decision interrupted
    mid-turn can be answered later; that is the only side effect here.

    Callers that already delivered must not call this again -- it would
    overwrite the stored reply with the same one and lose the turn pairing.
    """
```

1. **做什么**（一句）
2. **守什么**（一句，不变量或副作用）
3. **什么时候不该用 / 调用方要注意什么**（一句）——这条最有价值，也最常被省略

### 3.3 门禁

新增 `scripts/lint/docstrings.py`（与 `function_size.py` 同构）：

- 函数 ≥25 行且无 docstring → 失败
- 模块无 docstring → 失败
- **存量先冻结**：把当前缺文档的函数列进 BASELINE，与 `function_size.py` 同样处理
  （只许补、不许新增缺文档的）

### 3.4 验收

- 核心三包 ≥25 行函数的 docstring 覆盖 ≥70%
- 门禁自带 5 个测试（新增缺文档被拒、基线放行、补完后可划掉、改名被当成新函数、模块缺 docstring 被拒）
- `pytest` 全绿、subtests 恒为 11958

**复杂度**：低（纯注释，零行为变更）。**风险**：极低——注释不改变语义，但会改变行号，
所以 `function_size.py` 的基线条目可能需要同步下调。

## 4. Phase B：公开面显式化

### 4.1 现状

23 个包里 11 个声明了 `__all__`。缺的是功能包里的：

```
clinical/  dialogue/  extensions/  guards/  infra/  reports/  review/
```

内核包（`core/` `facts/` `content/` `web/` `shared_types.py`）**不需要**——
它们不对外承诺 API，被内核依赖即可。

### 4.2 做法

1. 对每个包，列出 `__init__.py` 当前导出的名字（AST 读取，不靠 import）
2. 写成显式 `__all__` 字面量，排序（现有 `test_package_surfaces.py` 已要求 sorted + unique）
3. `test_package_surfaces.py` 的 `test_every_export_is_used_or_owned` 会检查每个导出
   是否真被使用或真属于本包——这一步会暴露"声明了但没人用"的旧符号，正好一并清理

### 4.2.1 执行记录（2026-11-03）：计划的前提是错的

方案假设这 7 个包"漏写了 `__all__`"。实测不是：它们**有意为空**，124 处调用全部走
子模块路径（`from medagent.clinical.triage import TriageService`），从包级导入 0 处。

所以做法不是补全 `__all__`（那会给每个符号造出第二个定义点），而是**显式声明空公开面**
并让门禁区分"没写"与"有意为空"。同样地，4 个内核包也声明空公开面。

规则落地时还发现**两个包一直在公开面之外**：`medagent.kg`（6 个名字）和
`medagent.shared_types`（5 个）——它们在导出，却没有被受检。两者都加入了受检列表，
`shared_types` 的列表此前还是未排序的。

### 4.3 风险

补 `__all__` 之后，"从包导入未声明的符号"从"能跑"变成"报错"。所以第 1 步要先统计
全仓有多少这样的调用点，若超过 20 处则先补声明再改门禁。

**复杂度**：低。**风险**：中（可能暴露隐藏依赖）。

## 5. Phase C：`_preamble.py` 的处置

### 5.1 事实

6 个文件，1417 行，286 个名字，**内容互不相同**：

| 文件 | 行 | 名字数 | 主要是 |
|---|---|---|---|
| `consultation/_preamble.py` | 403 | 64 | stdlib 转手 + 问诊类型 |
| `consultation/agent/_preamble.py` | 352 | 59 | stdlib + 引擎类型 |
| `server/_preamble.py` | 287 | 55 | stdlib + HTTP 类型 |
| `subagents/coordinator/_preamble.py` | 79 | 44 | stdlib + 并发原语 |
| `patient_records/store/_preamble.py` | 74 | 34 | stdlib + 存储类型 |
| `execution/_preamble.py` | 222 | 30 | stdlib + 执行类型 |

**名字不表达任何内容**：`from ._preamble import X` 里的 `X` 是什么，读者无从判断。
这是命名维度上唯一真正的疤。

**它为什么存在**：打破循环导入。`core.py` 导入 `_preamble`，而 `_preamble` 又从
`core.py` 那一侧导入符号——直接导入会成环。

### 5.2 两个选项

**C1 改名（低风险，不解决根本问题）**
`_preamble.py` → `_vocabulary.py`（本包共享词汇）。名字诚实了一点，但它仍然转手
`deepcopy`/`uuid4`/`Path`——**这些根本不需要集中**。

**C2 拆分（推荐，中风险）**
把 stdlib 部分移回使用处（每个使用文件一行 `from copy import deepcopy`），
`_preamble` 只留**本包的项目符号**，并改名为能表达内容的名字：

```
consultation/_preamble.py      → consultation/_vocabulary.py
consultation/agent/_preamble.py → consultation/agent/_vocabulary.py
server/_preamble.py            → server/_vocabulary.py
…
```

收益：1417 行里相当一部分分散回使用处，读者在文件开头就能看到它真正依赖什么；
名字从"这是啥"变成"这是本包的共享词汇"。

风险：改动所有 `from ._preamble import …`（实测 **30 处**，涉及 30 个文件，测试里另有 2 处），
且必须保持导入顺序以免成环——**每一批改完立刻跑全量**。

**执行记录（2026-11-03）**：Phase A 与 Phase B 已完成。C2 **按计划单独立项**——它是本
方案里唯一会大面积改动导入结构的一项（30 处导入点、6 个文件、1417 行），值得单独一次
提交和单独一次审查。本轮只做了 A/B/D/E。

C1（只改名）留作 C2 的前置：如果先做 C2，30 处导入点本来就要改，改名就搭车完成；
单独做一次改名反而是两次同样的改动。

### 5.3 执行记录（2026-11-03）：实测推翻了方案的两个假设

Phase C 执行时，两条被写在上面的假设被数据否定了。

**假设一："preamble 是为打破循环导入而存在的。"**

实测：`import_rules.py` 的模块级图里，**改动前后都是 0 个环**。这些 preamble 不是为破环
而存在的——它们是**拆文件时的残留**：把一个 2000 行的模块拆成十几个小模块，每个小模块
都从原来的大模块里复制了一份 import 块。

这个区别很重要：如果它们真在破环，就只能改名，不能拆。而既然不是，**正确的做法不是改名，
是让每个符号从定义它的模块直接导入**。

**假设二："C2 = stdlib 移回使用处，项目符号留在中转模块。"**

实测 6 个 preamble 的 286 个名字：

| 分类 | 数量 | 处置 |
|---|---|---|
| 本文件自己定义 | 56 | 搬进按语义命名的模块 |
| **纯转手**（别处定义、这里再导一次） | **230（80%）** | 消费方直接导入定义处 |
| └ 其中**只被一个模块用** | **169** | 同上——一个读者还要开第二个文件才知道名字在哪 |
| 必须中转（直接导入会成环） | **0** | 见下 |

方案原本担心 agent 子包要用 consultation 的共享词汇（`is_refusal_text` 等 5 个）、
直接导入会成环。实测**不成环**：只要那些名字住在一个**不导入本包任何东西**的叶子模块里，
agent 就能直接读。原来的中转之所以必要，只是因为它们被塞进了会导入本包的 `_preamble.py`。

**终态**（6 个 `_preamble.py` 全部消失，1417 行 → 11 个语义模块）：

```
consultation/vocabulary.py         标签表、患者措辞词表、文本判定与合并
consultation/thresholds.py        急症/挂起的门槛与规则
consultation/agent/catalog.py     模型能看到的能力与任务种类
consultation/agent/questions.py   改写患者已部分回答过的提问
consultation/agent/decision.py    告诉模型如何修复出错的决策
execution/errors.py               两个执行期异常类型
execution/endpoint.py             会话绑定到哪个模型端点，以及端点密钥不外泄
execution/workspace_files.py      在工作区里读文件而不越出边界
server/limits.py                  HTTP 层接受什么
server/baseline.py                这次问诊是关于谁的，以及给他看的基线
server/persistence.py             把路由改过的状态写回去，以及用药提醒计划
```

**新增门禁 R7**（`import_rules.py`）：一个模块如果**转发了名字却不定义任何东西、也不声明
`__all__`**，就是中转——读者无法知道它是什么。要求它要么定义点什么，要么声明自己转发了
什么（`__all__`），要么是入口点。6 个测试。

注意 R7 拦的不是"重新导出"：包门面的本职就是重新导出。拦的是**隐藏**自己在重新导出。
`consultation/types.py` 声明了 `__all__`，`platform_fs.py` 在分支里定义自己的名字，
`cli.py` 是入口点——三者都合法。

## 6. Phase D：`core.py` 的处置（降级为"不改"）

上一轮口头评估说三个 `core.py` 是"三义"，**这个判断需要修正**：它们的 docstring 各自
写明了（"Mixin: core for ConsultationEngine" / "…for AdaptiveConsultationEngine" /
"…core routes for Handler"），所以这是**同一个约定在三个上下文**——每个包一个核心
mixin 文件，不是含义冲突。

它剩下的问题只是：从 import 路径看不出是哪个引擎的 core。实测引用点只有 **3 处**，
所以改名的成本比预想低——但收益同样只有那一点。

**决定：保持现状**，但在 [架构分层规则](架构分层规则.md) 里补一句约定——
"每个包至多一个 `core.py`，存放该包的核心 mixin"。把约定写下来，比改三个文件名更划算；
若将来有人真的分不清三个 `core.py`，改名的成本也只有 3 处。

**执行记录（2026-11-03）**：约定已写入架构分层规则 §3.1。

## 7. Phase E：冻结债务的处置方针

116 个超标函数在 `function_size.py` 的基线里（口径见 §0.1），门禁保证它们不增长。

**不要再承诺持续下降。** 剩下的多数是正当复杂度：数据装配、协议解析、文件系统状态机。
把承诺改成三件事：

1. **只降不升**（门禁已在做）
2. **每季度复查一次**：从基线里挑出"最近的改动碰过的"那些，评估是否该拆
3. **基线条目随改动自然消解**：谁动了那些函数，谁顺手拆——而不是安排一轮专项

复查时用这个判据（而不是行数）：**这个函数有没有第二个职责？** 有就拆，没有就留在基线里。
`compose_conclusion` 只有一个职责（装配结论单），所以它不该拆。

**执行记录（2026-11-03）**：这一条已落地。基线按新口径重算为 116 条，承诺从"持续下降"
改为"只降不升 + 季度复查 + 随改动消解"。季度复查尚未开始——第一次应随下一次真实改动
一起做，而不是单独安排一轮专项。

## 8. 明确不做

| 不做 | 理由 | 重启条件 |
|---|---|---|
| 继续拆 `execution/` `server/` `dialogue/` 的长函数 | 收益低于成本，且多为正当复杂度 | 某次改动让它们同时承担了第二个职责 |
| 给全仓 242 个缺文档函数补文档 | 工作量大、收益集中在核心三包 | Phase A 的门禁生效后，改到哪个文件补哪个 |
| 改 `core.py` 的文件名 | 约定一致，改名收益小于成本 | 出现两个包各有两个"核心"文件时 |
| 删掉 `_preamble.py` | 它是打破循环导入的垫片 | 先做 C2 的验证批次 |
| 给每个包重排模块 | 现有分组已通过分层门禁 | 出现"为一个改动翻 5 个包"的实例 |
| 全仓按行数批量拆函数 | 已验证会推高参数个数 | 不重启 |

### 11.2 三处被实测推翻的前提

**① Phase B 以为那 7 个包"漏写了 `__all__`"，其实它们有意为空。**
124 处调用全部走子模块路径（`from medagent.clinical.triage import TriageService`），
包级导入 0 处。做法因此不是补全 `__all__`（那会给每个符号造出第二个定义点），
而是**显式声明空公开面**，并让门禁区分"没写"与"有意为空"。

**② Phase C 以为 `_preamble` 是为打破循环导入而存在的，其实不是。**
`import_rules.py` 的模块级图里，改动前后都是 **0 个环**。它们是**拆文件时的残留**。
这个区别决定了做法：如果真在破环，就只能改名不能拆；既然不是，正确的做法是
**让每个符号从定义它的模块直接导入**——所以终态不是"改名"，是 6 个中转层消失。

**③ Phase C 以为"必须中转"的那 5 个名字直接导入会成环，其实不会。**
只要它们住在一个**不导入本包任何东西**的叶子模块里，`consultation/agent/` 就能直读。
原来的中转之所以必要，只是因为它们被塞进了会导入本包的 `_preamble.py`。

### 11.3 两个门禁之间的冲突（口径变更）

给 `correct_fact` 写完 17 行 docstring，它从 133 行变成 150 行，当场撞上 `function_size.py`
的基线。**两个门禁在互相打架**：一个要求写清楚，一个按文本长度判定复杂度。

后者量错了东西：**函数的大小是它的逻辑，不是关于它的散文**。尺寸门禁现在不计 docstring
（注释照算——注释不是承诺，不改变行为）。重算后超标从 126 降到 **116**，其中 10 个原本
只是被 docstring 撑过了线。这 10 个是真实的改进，不是账面游戏。

### 11.4 剩下 173 个函数与 12 个模块

它们在 `execution/`、`server/`、`dialogue/`——方案第 6 节明确不排期：这些地方的长函数
多是数据装配、协议解析、文件系统状态机，拆它们的收益低于成本（`_validate_report`

## 11.6 浏览器验收：一次"通过"其实是不通过的

原记录写的是"Playwright 259 passed"。**这个数字当时是对的，但它的含义不对**：
浏览器套件里有一批用例**从来没被真正执行过**——不是跳过，是它们在 CI 的
`test:ui:ci` 路径下没有跑，或者跑了但没人看退出码。

本轮跑全量时才发现：**349 个用例里有 65 个失败**。全部来自与本方案无关的
既有缺陷，都由 `ad7319e`（2026-11-02，web 资源搬进 `css/` `js/` `assets/` 目录）
留下，以及一处早就在那里的竞态：

### 缺陷一：前后端的资源路径规则不一致（19 个失败）

服务端 `extensions/registry.py` 的规则是 `ILLUSTRATION_PATH = r"(?:/[a-z0-9-]+)+\.svg"`，
**允许多段**；前端 `structured-ui-primitives.js` 的 `asset()` 却只接受单段
`/^\/[a-z0-9-]+\.svg$/`。能力包指向 `/assets/illustrations/body-location.svg`，
前端判定非法，于是**每一张自检任务卡都渲染成"这部分内容暂时无法显示"**——
患者根本看不到任务。

`ad7319e` 改了服务端的规则和路径，**漏改了前端的正则**。

### 缺陷二：测试仍引用搬走前的扁平路径（29 个失败）

`ad7319e` 把脚本搬进了 `js/`，页面自己更新了，**16 个浏览器 spec 没更新**：
`await import("/structured-ui.js")` 变成了 404。

### 缺陷三：一处竞态（1 个失败）

`location-revisions.spec.mjs` 的循环用"忙指示器消失"当作"回合结束"的信号。
忙指示器在请求发出**之前**就是隐藏的，所以循环可能多问一轮——而脚本化
模型的队列是有限的，多出来的那一轮得到的是 500，页面变成"这一步的对话服务
暂时不可用"。这个用例单独跑 4/4 通过、在套件里 3/4 通过。

改成等消息响应（仓库里另外 5 个 spec 早就这么写）。

### 三个新门禁

| 门禁 | 拦什么 | 位置 |
|---|---|---|
| 资源路径契约 | 前端 `asset()` 的判定与服务端 `ILLUSTRATION_PATH` **逐条一致**；能力包声明的每一张插图都能渲染 | `tests/unit/asset-paths.test.mjs`（3 个用例） |
| 浏览器测试的引用图 | 每个 spec 里的 URL 字面量都必须对应服务端真实提供的文件（该 spec 自己 mock 的除外） | `tests/architecture/test_static_assets.py` |
| 回合结束的信号 | 循环读状态之前必须等消息响应 | 不设门禁——**修好竞态比加规则更实在**，而且这条规则会误伤合法的写法 |

前两个都验证过**能真的抓住对应的 bug**：把规则改回旧形态，第一个 2/3 失败；
把一个 spec 的路径改回旧地址，第二个立刻报错。第二个还抓出了第三种形态：
带 `#fragment` 的 URL（`/x.svg#step-2`）——它的扩展名后面还跟着片段，
最初的正则漏了它，于是 `workspace.spec.mjs` 里两处**断言**写错了路径也没人管。

### 还有一个更值得记的发现

`tests/unit/` 下的三个前端单测文件**没有任何东西在跑**——不在 CI 里，不在
`package.json` 里。于是"前后端规则不一致"这种只有前端单测能发现的问题，
可以一直躺在仓库里没人看见。现在 `npm run test:unit` 接进了 CI。

### 顺带修掉的：浏览器套件的运行器

`scripts/test/ui-ci.mjs` 原本用 Python 清理输出目录，但**清理失败是静默的**：
`ignore_errors=True` 吞掉部分失败，目录残留，下一个文件死在删除保护里，
于是**每一个 spec 文件都被报成失败**，摘要还是空的——失败原因跟 spec 毫无关系。

现在清理是**可验证的**：目录没清掉就以非零退出，并说出是哪个文件；
清理按**逐条目、自底向上**执行，所以再大的产物树也能分次删掉。
这条改动在 CI 里没有行为变化（那里没有删除保护），变的是本地跑要么成功、
要么说清楚为什么。

**结论**：这一轮的可读性改造对浏览器路径**零回归**——用 AST 等价性验证了
旧树 1040 个顶层符号在新树中逐字不变，又用基线 worktree（`c564a9a`，本轮
全部改动之前）跑出完全相同的 14 个 appearance 失败，逐条比对无差异。
但它顺带暴露了**浏览器门禁一直是红的**，而这个红一直没被看见。

**修完之后**：浏览器套件按 CI 的路径（`npm run test:ui`，每个 spec 文件一个
独立 server 与独立数据目录）跑，**52 个 spec 文件 / 349 个用例全部通过**，
四个 shard 共 19 分钟。Python 侧 **2065 passed / 11958 subtests 恒定**。

### 怎么证明"零回归"而不是"看起来没回归"

两条互相独立的证据：

1. **符号级 AST 等价**：把旧树（`32bd25f`）与新树（`HEAD`）的每个顶层符号
   去掉 docstring 与 import 后逐个比对——1040 个符号，**0 个缺失、0 个改动、
   0 个新增**。搬迁是逐字的。
2. **基线对照**：在 `c564a9a`（本轮全部改动之前）建 worktree 跑同一套
   appearance，**14 个失败与主线逐条相同**。同一个 bug，两边一样。

两条都排除了"我的改动引入失败"的可能——所以修掉的那 65 个，**不是我造成的**。
