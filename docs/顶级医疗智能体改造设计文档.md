## 0. 这份文档要解决什么

当前系统的问题不是某个函数写得差，而是**流程的组织方式**：问诊主流程是一条不断加长的硬编码瀑布，安全判断靠关键词表，选题靠"填表顺序"，且确定性引擎与自适应（LLM）引擎两套流程并行维护。本设计的目标是在**完整保留问诊内核**的前提下，把系统改造成一个临床推理驱动、评测驱动的医疗智能体，具体分五步：

1. 分诊从单层关键词匹配升级为三层防御（规则兜底 + 语义召回 + 推理复核），且每轮只计算一次；
2. 主流程从 if 瀑布拆成显式管线，两个引擎共用一条管线，只在"规划策略"上分叉；
3. 核心状态从"事实填表"升级为"事实 + 鉴别诊断假设空间"，选题按红旗优先级与信息增益打分；
4. 评测从外挂验收升级为发布门：没有可量化的临床指标基线，任何改动不得合并；
5. 打通纵向闭环：随访结局回流医生复核与评测语料，形成数据飞轮。

设计原则（贯穿全文）：

- **内核不动摇**：第 1.2 节列出的契约在任何阶段不得破坏，每阶段用特征化测试证明未破坏。
- **模型提议、规则裁决、确定性写入**：LLM 永远不直接写状态、不直接决定安全等级；一切模型输出先经确定性校验再落盘。这一模式在现有的计算能力调用（`run_capability` 拒绝 `model_proposal` 直接执行）中已有雏形，本设计将其推广为全局规范。
- **召回优先于精确**：凡涉及安全的判断，宁可误报升级，不可漏报放行；精确率靠后续复核层挽回，漏检没有挽回机会。
- **一切可测**：每个新组件都必须自带离线评测入口和指标，否则不进入实施清单。

## 1. 目标与非目标

### 1.1 目标

- G1（安全）：急症红旗在评测语料上的召回率可测、可回归，目标见 5.1；分诊判断每轮单次计算、全程可审计。
- G2（架构）：问诊主流程收敛为一条显式管线；新增问诊能力（如新的输入类型）只需新增一个处理器并注册，不再修改主流程代码。
- G3（推理）：问诊选题由鉴别诊断假设空间驱动，系统能解释"为什么问这个问题"（指向哪个假设的区分或哪条红旗的排除），解释随事件落盘。
- G4（评测）：建立四类评测资产（红旗语料、模拟患者、OSCE 式病例、行为基线轨迹），接入发布门；每次发布有机器可读的评测报告。
- G5（闭环）：问诊结束后可登记随访与结局，医生复核（`background_review`）标注回流评测语料。

### 1.2 内核保护清单（不可变契约）

以下行为是现有内核的资产，改造期间必须逐项保持，并由 3.1 的行为基线测试集锁定：

- K1 **急症门不可绕过**：任何患者可见回复产生之前，急症/紧急判断必须已完成；已命中急症时只允许发布控制器生成的急救回复且必须包含 120 指引（现由 `ReplyPublicationGate` 强制，见 `docs/发布门、阶段提交与临床评测框架.md`）。
- K2 **事实模型**：`Fact` 的结构（key/value/assertion/source/turn_id/evidence/structured_input）与"原话可溯源"语义不变；更正走 `correct_fact`/`restore_fact` 的既有路径与版本校验（`_check_fact_version`）。
- K3 **事件审计**：所有状态变更与回复发布写入 `EventStore`；阶段变化只在回复真正发布时经 `commit_phase` 提交（`state_transitions.py`），不得把未发布的中间阶段写进审计轨迹。
- K4 **阶段语义**：`Phase` 枚举的患者可见语义（opening / emergency_screen / history / background / observation / summary / closed）不变；内部可扩展，但患者可见的阶段集合与含义在 v1 不变。
- K5 **对外接口**：`ConsultationEngine.submit(session_id, UserInput) -> AgentReply` 的签名、`AgentReply` 的患者可见字段、`server.py` 依赖的会话接口不变。
- K6 **计算安全**：计算类能力必须经用户核对输入卡后执行（`run_capability` 现有约束），模型提议不得直接执行。
- K7 **就诊对象边界**：`consultation_subject.py` 的对象隔离语义不变（问诊对象与会谈草稿隔离，见对应设计文档）。
- K8 **确定性降级**：模型服务不可用时，系统降级为确定性问诊（现有 `ConsultationEngine` 行为），不得中断已开始的会谈（`agent.py` 现有 `service_error` 降级路径的语义保留）。

### 1.3 非目标（范围纪律）

- 不扩展通用执行底座、桌面应用、文件工作区等非医疗主线能力；相关代码冻结，只做与问诊接口相关的兼容性维护。
- 不做诊断结论的自动确诊：系统输出始终是"分流建议 + 结构化摘要 + 鉴别诊断参考（供医生复核）"，不向患者呈现确诊口吻。
- 不在本设计内解决数据治理（加密、留存、删除）与监管申报问题，仅在风险登记册（第 8 节）中标注为上线前置条件。
- 不更换模型供应商抽象（`backends.py` 的 `DecisionBackend` 保留），但要给它加结构化输出与预算约束（见 4.7）。

## 2. 现状诊断（与代码对照）

以下结论均来自基线 commit 的实际代码，评审时可逐条复核：

1. **主流程瀑布**：`ConsultationEngine._submit`（`consultation.py` 约 923–1092 行）以十余个早返回分支串起全部问诊行为：急症求助 → 过期动作校验 → 定位答案预处理 → 定位修改 → 会话关闭 → 就诊对象控制 → 重复测量 → 摘要核对 → 图示任务 → 当前问题解释 → 无主动问题的自由输入 → 分诊评估 → 急症/紧急回复 → `_plan_next`。分支顺序即语义，新增能力只能继续往链上插段。公开方法 `submit` 之外，计算相关动作又另有一组 `_check_calculation_action` / `_handle_calculation_action` 等并行入口，同一引擎内存在多条进入路径。
2. **两套流程**：`agent.py` 的 `AdaptiveConsultationEngine` 覆写 `_submit`（约 235–481 行），维护自己的前置处理，再进入 `_run` 的最多 6 步工具循环（约 617 行起），每步调用模型决策、执行工具、计数写入（`record_facts` 每轮上限 2 次为硬编码）。急症检查、事实写入在两条路径中各有实现，存在行为漂移风险。
3. **分诊单层且重复计算**：`triage.py` 的 `scan_text` 是短语精确匹配（`EMERGENCY_RULES` 6 条规则 + `NEGATIONS` 固定词表 + `_not_negated` 前缀窗口判断），`assess` 在此之上叠加少量硬编码组合规则（如口腔主诉 + 活动相关标签）。同一轮输入在 `consultation.py` 中被 `scan_text` 至少扫描 5 处（过期校验豁免、紧急文本替换、定位预处理跳过、直达急症判断等），`agent.py` 中另有 4 处，结果一致性靠巧合。
4. **选题是填表顺序**：`_plan_next`（约 1260 行）从静态题库（`content/questions.json`，约 4.8KB）中取"最早阶段、fact_key 未记录"的问题，阶段内由 `QuestionRanker.choose` 排序；`_phase_rank` 对 observation/summary 落到默认值 9。问题与临床假设无关，无法表达"为了区分 A 与 B 而问"。
5. **语义理解靠正则**：`assertion_evidence.py` 文件头自述为 "Bounded checks of Chinese assertion evidence, not a clinical language parser"——否定与不确定表达靠短语表 + 正则窗口，与分诊层同样脆弱，且两套短语表独立维护。
6. **状态松散**：`CaseState` 上挂有 `calculation_feedback`、`observation_feedback`、`background_review`、`pending_input` 等字典型字段，`agent.py._run` 直接读写其中的 `["processing"]`、`["forwarded"]` 标记。流程进度没有单一事实来源。
7. **评测有合同、无基线**：`scripts/evaluation/medical/evaluate_medical_release.py` 只接受外部临床审核标记 `approved` 的病例做确定性评分（合同设计是诚实的），但仓库内 `docs/evaluations/` 只有 2026-10-15 至 17 三天的工程评测记录，没有临床标注基线。也就是说：**当前系统的临床质量（尤其红旗漏检率）在数值上是未知的。**
8. **可复用的好资产**（改造的地基，不是推倒重来的理由）：`ReplyPublicationGate` 确定性发布门、`commit_phase` 阶段提交、完整的 `EventStore` 审计与 trace/decision 标识、`Fact` 证据溯源、`assertion_evidence` 的否定/不确定语料、`background_review` 后台复核、`patient_records` 纵向记录、约 80 个测试文件（其中问诊相关如 `test_consultation.py`、`test_state_consistency.py`、`test_consultation_interrupt.py` 可直接扩为行为基线）。

## 3. 目标架构总览

### 3.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│ 患者可见层    server.py / desktop（不改接口，K5）             │
├─────────────────────────────────────────────────────────────┤
│ L4 发布与审计层（保留并强化）                                  │
│   ReplyPublicationGate · commit_phase · EventStore          │
├─────────────────────────────────────────────────────────────┤
│ L3 对话管线层（新）                                           │
│   TurnPipeline：有序处理器注册表，短路语义显式化               │
│   处理器：安全前置 / 输入归一 / 动作路由 / 事实写入 / 规划 / 收尾 │
├─────────────────────────────────────────────────────────────┤
│ L2 推理与规划层（新）                                         │
│   Planner 策略接口：RulePlanner（现行为）→ DifferentialPlanner │
│   鉴别诊断工作区：假设、证据链、红旗、待区分问题               │
├─────────────────────────────────────────────────────────────┤
│ L1 临床状态层（收敛）                                         │
│   CaseState v2：Fact 集合（K2 不变）+ 类型化子状态 + 假设工作区  │
├─────────────────────────────────────────────────────────────┤
│ L0 安全层（新）                                               │
│   TriageService：规则层 ∪ 语义层 ∪ 推理复核层，每轮单次计算     │
│   结果 TriageVerdict 随 TurnContext 传递，任何层不得绕过（K1）  │
├─────────────────────────────────────────────────────────────┤
│ 横切：TurnContext（回合上下文）· 评测面（离线评测 + 在线影子）   │
│       模型网关（backends + 结构化 schema + 预算）              │
└─────────────────────────────────────────────────────────────┘
```

层级约束：

- L0 的结论（`TriageVerdict`）只能被 L3/L4 读取和执行，任何上层不得下调安全等级；上层只能上调（例如规划器发现新红旗线索时可请求 L0 复评，但复评仍走 L0 全层）。
- L2 只产出"提议"（下一个问题、假设更新、摘要草稿），落盘前必须经 L1 的确定性校验器（证据引用存在、断言合法、写入配额），与现有"模型提议 → 用户核对 → 确定性执行"的模式一致（K6）。
- L4 保持现有实现与语义，仅在事件字典中增加新字段（管线处理器名、分诊三层明细、假设工作区版本），不改变既有事件类型。

### 3.2 行为基线（先于一切改造）

在动任何代码前，先把 K1–K8 冻结成可执行的基线：

- 从现有测试中抽取并补齐一组**轨迹用例**（transcript fixtures）：正常全程问诊、急症直达、紧急升级、摘要更正、定位修改、就诊对象切换、重复测量、计算请求、模型不可用降级，共 9 类场景，每类至少 3 条（含变体说法）。
- 轨迹用例的断言对象是患者可见行为：回复 `kind`、阶段序列（以 `commit_phase` 提交为准）、写入的 Fact 集合、风险等级序列。不断言内部调用顺序。
- 基线在 CI 中对主分支与改造分支同等运行；改造分支允许新增用例，不允许在没有评审记录的情况下修改既有用例的期望值。

## 4. 详细设计

### 4.1 TurnContext 与单次分诊

**问题**：同一轮输入被 `scan_text` 重复扫描 ≥5 次，且各处扫描对象不完全一致（有的扫原文、有的扫定位替换后的文本），一致性无保障。

**设计**：引入回合上下文对象，作为一轮 `submit` 内唯一的数据通道：

```python
@dataclass
class TurnContext:
    session_id: str
    turn_id: str
    raw_text: str                 # 患者原始输入
    normalized_text: str          # 归一化文本（定位结构化替换等处理后）
    choice_value: Optional[str]
    triage: TriageVerdict         # 本轮唯一分诊结论，进管线前计算
    assertion_map: AssertionMap   # 本轮断言/否定/不确定分析，单次计算
    state_revision_at_start: int
    trace: List[str]              # 处理器执行轨迹（调试与审计用）
```

规则：

- `TriageVerdict` 与 `AssertionMap` 在管线入口计算一次，处理器只读。任何处理器若处理了会改变语义的文本（如定位修订产生新文本），必须显式声明 `requires_retriage=True`，由管线在该处理器后统一复算一次，并把复算原因写入事件——把现在散落的重复扫描收敛成**一个受控的复算点**。
- `assertion_evidence.py` 的短语/正则分析升级为 `AssertionMap` 的规则实现，接口保留，内部实现允许在阶段三替换为模型辅助版本（见 4.7），分诊层与事实解释层共用同一份分析结果，消除两套短语表。

### 4.2 三层分诊（L0）

```python
@dataclass(frozen=True)
class TriageVerdict:
    level: RiskLevel              # EMERGENCY / URGENT / ROUTINE / UNDETERMINED
    triggers: Tuple[str, ...]     # 患者可见的触发说明（沿用现有文案风格）
    layer_hits: Dict[str, Tuple[str, ...]]  # 每层的命中明细，进审计
    red_flag_ids: Tuple[str, ...] # 命中的红旗定义 id（语料与评测对齐用）
    computed_from: str            # 输入文本的哈希，防错配
```

- **第一层·规则层（保留并整理）**：现有 `EMERGENCY_RULES` 与 `assess` 中的数值规则（体温、年龄、严重度、轨迹）迁入，改为**红旗定义表**驱动：每条红旗是一个带 id 的定义（短语集、数值条件、组合条件、目标等级、患者文案），定义表是数据文件而非代码常量，新增红旗只改数据 + 加评测用例。否定处理沿用 `_not_negated` 窗口逻辑，但窗口与否定词表从 `assertion_evidence` 统一引用。
- **第二层·语义层（新增）**：接口 `SemanticRedFlagProvider.scan(text, assertion_map) -> List[RedFlagHit]`。实现分两步走：阶段一先用"红旗语料嵌入检索"（把每条红旗的标准问法与变体说法做成向量库，输入文本分句检索，超阈值命中）；阶段三可替换/并联一个小分类模型。语义层只许上调等级，不许下调规则层结论。提供方不可用时静默降级为仅规则层，并写 `triage.semantic_unavailable` 事件。
- **第三层·推理复核层（新增，阶段三）**：当规则层与语义层结论为 ROUTINE/UNDETERMINED 且本轮出现新主诉或症状变化时，用决策模型做一次受限复核：输入为本轮文本 + 已确认事实摘要 + 红旗定义清单，输出必须是结构化 schema（命中红旗 id 列表 + 逐条证据引用），经确定性校验（id 必须存在、证据必须是原文子串）后才生效。复核层同样只许上调。
- **合并语义**：三层取并集，等级取最高。分歧（层间不一致）全量记录 `triage.layer_disagreement` 事件，作为语料挖掘与医生复核的输入——分歧集就是下一批标注语料的来源。
- **性能**：规则层与语义层在本轮入口并行执行，目标 P95 增量延迟 < 300ms；推理复核层只在触发条件满足时调用，计入 4.7 的回合预算。

### 4.3 对话管线（L3）

**处理器协议**：

```python
class TurnHandler(Protocol):
    name: str
    requires_retriage: bool = False
    def handle(self, ctx: TurnContext, state: CaseState) -> Optional[AgentReply]:
        """返回 AgentReply 表示短路本轮；返回 None 表示继续下一个处理器。"""
```

**注册顺序即现有语义顺序**（把瀑布的隐含顺序显式化，行为与基线对齐后再允许调整）：

| # | 处理器 | 对应现有逻辑 | 短路条件 |
|---|---|---|---|
| H1 | EmergencyHelpHandler | `_requested_emergency_help` | choice 为请求急救 |
| H2 | StaleActionGuard | 过期动作校验与 `turn.rejected` 事件 | expected_action_id 不匹配且未命中急症 |
| H3 | DirectEmergencyHandler | 直达急症判断与 `_emergency_reply` | `ctx.triage` 为 EMERGENCY |
| H4 | LocationRevisionHandler | `_handle_location_revision_action` 等 | 定位修改动作 |
| H5 | ClosedSessionHandler | CLOSED 阶段回复 | 阶段为 CLOSED |
| H6 | SubjectControlHandler | `_subject_control`（K7） | 对象切换/边界动作 |
| H7 | CalculationActionHandler | `_check/_handle_calculation_action`（K6） | 计算相关动作 |
| H8 | ObservationActionHandler | `_handle_observation_action`、重复测量 | 测量反馈动作 |
| H9 | SummaryReviewHandler | SUMMARY 阶段核对/确认 | 阶段为 SUMMARY |
| H10 | TaskResultHandler | `_try_task_result` 图示任务 | 存在 active_task 且输入为其结果 |
| H11 | AnswerIntakeHandler | active_question 解释、年龄校验、`_record_fact`、自由输入记为 unsolicited_note | 否（写入后继续） |
| H12 | RiskEscalationHandler | 分诊后 EMERGENCY/URGENT 回复 | 写入后复评等级升高 |
| H13 | PlanningHandler | 调 Planner 产出下一问/收尾（见 4.4） | 否（管线终点） |

约束：

- 管线执行器负责统一的事件记录（`turn.user_message`、每处理器的进入/短路、`_record_reply` 等价物），处理器内不得自行记录回复。
- 两个引擎合并：`AdaptiveConsultationEngine` 不再覆写 `_submit`；其模型决策循环迁入 `AdaptivePlanner`（4.4）与 H11 的模型辅助解释路径，安全与写入路径与确定性引擎完全共用。`decision_wait` 的抢占/中断语义保留在模型网关层（4.7），不进入管线。
- 每个处理器独立可测：给定 CaseState 快照 + TurnContext，断言其回复或放行。现有 `test_consultation*.py` 的用例按处理器重新归类，覆盖率不降。

### 4.4 规划器策略（L2）与阶段图

**Planner 协议**：

```python
class Planner(Protocol):
    def plan(self, ctx: TurnContext, state: CaseState) -> PlanAction: ...
# PlanAction = AskQuestion(question_id | generated, reason) 
#            | OfferTask(task_id, reason) 
#            | ProposeHypothesisUpdate(update)   # 阶段三
#            | Finish(summary_draft)
# reason 必填且必须可落盘审计：指向缺失字段 / 待区分假设 / 待排除红旗
```

- `RulePlanner`：封装现有 `_plan_next` + `_offer_task` 的行为，作为 v1 默认与降级策略（K8）。
- `AdaptivePlanner`：封装现有模型工具循环，但工具面收敛为 PlanAction 的提议通道；模型每轮的步数与写入配额从硬编码改为配置（`execution_limits.py` 同级新增 `planning_limits`），且写入仍走 L1 校验器。
- `DifferentialPlanner`：阶段三启用，见 4.5。

**阶段图**：把 `Phase` 的线性 rank 改为显式转移图，患者可见语义不变（K4）：

- 允许的主干转移沿用现状：opening → emergency_screen → history → background → observation → summary → closed。
- 新增**受控回边**：任意阶段在本轮 `TriageVerdict` 升级或新出现红旗线索时，可回 emergency_screen 复筛（经 H3/H12 触发，`commit_phase` 记录 reason）；history 与 background 之间允许因更正/补录双向转移。
- 转移图是数据（邻接表 + 每条边的守卫条件），`_phase_rank` 退役；"下一步去哪个阶段"由 Planner 的 PlanAction 与转移图共同决定，图外的转移在校验器处拒绝并落事件。

### 4.5 鉴别诊断推理核（阶段三核心）

**假设工作区**（挂在 CaseState v2 上，随事实一同持久化）：

```python
@dataclass
class Hypothesis:
    id: str
    label: str                    # 供医生复核的表述，患者不可见
    category: str                 # 如 red_flag_condition / common_condition
    prior_band: str               # high / medium / low（定性档位，不向患者展示数值）
    status: str                   # active / supported / refuted / ruled_out_by_test
    evidence_for: List[EvidenceRef]     # fact_id + 原话引用
    evidence_against: List[EvidenceRef]
    red_flags: List[str]          # 红旗定义 id
    discriminating_questions: List[str] # question id 列表
    updated_at_turn: str
```

**更新协议**（模型提议、规则裁决）：

1. 每轮事实写入后，推理核被触发一次：输入为新增事实 + 当前工作区 + 红旗清单。
2. 模型（或规则映射表，v1 先行）提议假设增删改：新增假设必须附至少一条已存在事实的证据引用；标记 refuted/ruled_out 必须附反证引用或检查结果事实。
3. 确定性校验器逐条核对：引用存在、原文子串匹配、状态机合法（如 ruled_out 不可被无检查结果复活）。校验失败的提议整条丢弃并落 `reasoning.proposal_rejected` 事件，不部分采纳。
4. 工作区每次变更产生版本号，写 `reasoning.workspace_updated` 事件（含 diff 摘要），供后台复核回放。

**选题打分**（DifferentialPlanner）：

```
score(q) = 3.0 * redflag_coverage(q)          # 能排除/确认任一 active 假设的红旗
         + 2.0 * discrimination(q)            # 能区分 top 假设集合中 ≥2 个假设
         + 1.0 * requiredness(q)              # 处置/摘要必需字段（现 missing_required 语义）
         + 0.5 * freshness(q)                 # 与本轮新事实相关
         - 0.5 * burden(q)                    # 问题负担（敏感/重复/耗时，定义表标注）
```

权重为初始值，必须在评测集上调参并记录版本（5.3）。选题结果必须携带 reason：命中的假设 id 与红旗 id，患者侧文案仍用现有 `_ask` 的温和表述，reason 只进审计与复核界面。

**停止与弃权**：

- 当 active 假设集合中最高档位置信且关键红旗均已排除、必需字段齐全时，进入 summary（沿用现有 `_finish` 与摘要载荷，摘要的每条事实继续带 provenance）。
- 当出现以下情形时**强制弃权升级**（不给诊断倾向）：红旗无法排除且信息不足、假设集合为空且主诉持续、工作区连续 3 轮无有效区分进展。弃权回复为固定模板：说明不确定性、给出就医建议、提供摘要供面诊使用。
- 鉴别诊断内容**只出现在医生复核端与摘要的"待核实"区**，患者界面不展示疾病排名（非目标：不做自动确诊）。

### 4.6 状态模型收敛（CaseState v2）

- 把字典型字段收敛为类型化子状态：`CalculationState`、`ObservationState`、`SubjectState`、`ReviewState`（background_review）、`ReasoningWorkspace`（4.5）。每个子状态自带 `to_dict/from_dict`，序列化格式与现字段同构，老存档可直接读入（字段名不变，只加类型层），避免存储迁移。
- 子状态的变更必须走各自的方法（如 `ObservationState.mark_forwarded()`），禁止外部直接写字典键——把 `agent.py._run` 中散落的标记位读写全部收口。
- `state.revision` 语义不变；假设工作区版本与 revision 分开计数，避免推理更新污染既有的事实版本校验（K2）。

### 4.7 模型使用规范（模型网关）

- 所有模型调用经 `backends.py` 的 `DecisionBackend` + `decision_wait.py` 的等待/抢占机制，新增**结构化输出合同**：每次调用声明 schema（如分诊复核、假设更新、答案解释），网关负责 schema 校验与一次重试，仍失败则走降级路径并落事件。
- 系统提示词（现 `content/agent_prompt.txt`，约 19.6KB）按用途拆分版本化：规划提示、复核提示、解释提示分别成文，各自带版本号并写入事件，禁止再维护单一巨型提示词。
- 回合预算：每轮模型调用次数、token、时延设上限（配置项），超限即降级 `RulePlanner` 完成本轮——把现有 6 步/2 写硬编码改为可观测、可调的预算策略。
- 上下文构建（现 `agent.py._context` 约 120 行手工拼装）收敛为 `ContextBuilder`：按调用用途裁剪（复核只需事实摘要 + 红旗清单，不需要完整 transcript），并对"早期原话溯源"（`earlier_source_turns`）等既有机制保留等价物。

## 5. 评测体系设计

### 5.1 指标字典（v1 目标值，上线前由临床方复核签署）

| 指标 | 定义 | 数据来源 | v1 门槛 |
|---|---|---|---|
| 红旗召回率 | 红旗语料中应升级样本被正确升级的比例（按红旗 id 分别统计） | 红旗语料集 | 每条红旗 ≥ 0.99，总体 ≥ 0.995 |
| 红旗误报率 | 非红旗样本被升级至 EMERGENCY 的比例 | 红旗语料集 + 模拟患者 | ≤ 0.05（URGENT 误报 ≤ 0.15） |
| 分诊等级一致率 | 与临床标注等级完全一致的比例 | OSCE 式病例 | ≥ 0.90，且不允许"标注 EMERGENCY 判低"出现 |
| 鉴别诊断 Top-3 命中 | 标注鉴别诊断出现在工作区 top 档假设中的比例 | OSCE 式病例 | ≥ 0.80（阶段三起统计） |
| 问诊效率 | 达到收尾条件的平均轮次（同病例与基线对比） | 模拟患者 | 不劣于基线 +10% |
| 摘要事实准确率 | 摘要条目与事实表/原话一致的比例 | 摘要核查集 | ≥ 0.99 |
| 弃权恰当率 | 应弃权样本中正确弃权 + 不应弃权样本中未弃权 | OSCE 式病例 | ≥ 0.90（阶段三起） |
| 行为基线通过率 | 3.2 轨迹用例通过比例 | CI | = 1.00（硬门） |

### 5.2 四类评测资产

1. **红旗语料集**：每条红旗定义配套样本组——标准说法 ≥ 5 条、口语/方言/错别字变体 ≥ 10 条、否定对照 ≥ 5 条（"没有胸痛"类不得触发）、不确定表达 ≥ 3 条、组合症状 ≥ 3 条。样本带 `approved` 标注流程，复用 `evaluate_medical_release.py` 的审核合同（标注者 + 时间必填），未审核样本只许进"挖掘集"，不许进发布门统计。
2. **模拟患者**：用独立模型扮演患者（与被测系统不同模型/不同提示词，避免自证），按病例脚本（主诉、病史、性格参数：健谈/寡言/含糊/焦虑）与系统完成整场问诊，产出轨迹后由评分器按指标字典打分。模拟患者只用于工程回归与问题挖掘，**不得**作为临床有效性的证据（与现有评测文档的诚实声明保持一致）。
3. **OSCE 式病例集**：结构化病例（主诉脚本、标准问诊要点、标注分诊等级、标注鉴别诊断、应弃权标记），来源为临床方编写或脱敏改编，是本设计中唯一可支撑"临床质量"表述的数据集；规模目标：阶段三前 ≥ 100 例，覆盖红旗定义全集。
4. **行为基线轨迹集**：见 3.2，属工程资产，随代码版本管理。

语料/病例文件格式沿用现有评测输入合同（JSON + approved 元数据），新增字段：`red_flag_ids`、`expected_level`、`expected_differentials`、`abstain_expected`、`variant_of`（变体溯源）。

### 5.3 发布门

- 把 `ReplyPublicationGate` 的"确定性检查不通过则不发布"哲学提升到发布流程：CI 中新增 `medical-release-gate` 作业，依次跑行为基线（硬门）、红旗语料（硬门，门槛见 5.1）、模拟患者回归（软门：指标劣化超阈值需评审记录）、OSCE 病例（阶段三后转硬门）。
- 每次发布产出机器可读报告（JSON）+ 人读摘要，存入 `docs/evaluations/<date>/`（沿用现有目录习惯），报告包含：各指标数值、与上版 diff、分歧样本清单链接、签署人字段（临床指标部分必须由临床方签署，与现有合同一致）。
- 选题权重（4.5）、红旗定义表、提示词版本均为"需评测背书"的配置：变更必须附同版本评测报告，否则发布门拒绝。

### 5.4 影子运行与灰度

- **分诊影子**（阶段一）：新 TriageService 先以影子模式并行旧 `triage.py`，只记分歧事件，不影响回复；分歧经人工（含临床方抽样）确认新结论更优的比例 ≥ 95% 且无一例"新判低、旧判高且旧正确"后，才切换主判。
- **规划影子**（阶段二/三）：新 Planner 先对真实轨迹离线回放，再影子在线（只记录"本会问什么"），与实际所问的差异进复核队列；灰度按会话比例 5% → 25% → 100%，每档至少跑满一个评测周期且指标不劣化。
- 任一阶段的灰度出现红旗召回相关的线上分歧（新低旧高），自动回滚到上一策略并冻结发布，直到复盘完成。

## 6. 纵向闭环与复核飞轮

- **随访登记**：问诊关闭（summary 确认或弃权升级）时生成随访任务（`patient_records` 扩展）：建议复诊时间窗、需回收的结果类型（检查报告、面诊结论、用药反馈）。患者回填或医生录入后形成**结局标签**：最终诊断（脱敏编码）、分流是否恰当（恰当/过度/不足）、关键假设命中与否。
- **复核队列**：`background_review` 从"给建议"扩展为标注入口，优先排队三类样本——分诊层间分歧、规划影子分歧、结局标签为"分流不足"的病例。医生标注动作（确认/修正等级、确认/修正鉴别诊断）直接产出符合 5.2 合同的语料增量。
- **飞轮节奏**：每两周把新增标注语料并入评测集并出增量报告；语料只增不改（修正以新增版本实现），保证历史评测可复现。
- **边界**：结局数据只用于评测与规则/权重修订，不用于对单个患者的自动处置变更；涉及患者数据的留存与授权按第 8 节前置条件另行处理。

## 7. 分阶段实施计划

每阶段独立分支、独立 PR、独立验收；未通过验收不进入下一阶段。工作量为相对估计（S/M/L），非日历承诺。

### 阶段 0 · 基线冻结（工作量 S）
- 交付：3.2 的轨迹用例集（9 类场景）、CI 基线作业、红旗语料集 v0（先覆盖现有 6 条急症规则 + `assess` 数值规则的说法变体）。
- 验收：基线在主分支全绿；红旗语料跑出现状召回/误报数值（哪怕难看）并存档——这是全项目的第一个真实数字。

### 阶段 1 · 分诊单次计算与三层化（工作量 M）
- 改动：新增 `TurnContext`、`TriageService`（规则层迁移 + 红旗定义表数据化）；语义层接口与嵌入检索实现；管线入口统一计算，删除各处重复 `scan_text`（保留受控复算点）。
- 不动：`assess` 对外语义、`RiskAssessment` 结构、急症回复文案。
- 验收：行为基线全绿；红旗召回率不低于阶段 0 数值且目标红旗达标；影子分歧报告产出并完成一轮人工确认；单轮分诊计算次数可审计（事件中 `layer_hits` 齐全）。
- 回滚：`TriageService` 由配置开关切回旧 `triage.py` 直调。

### 阶段 2 · 管线统一与状态收敛（工作量 L）
- 改动：`TurnPipeline` + H1–H13 处理器落地；`AdaptiveConsultationEngine` 并入管线，模型循环迁为 `AdaptivePlanner`；`CaseState` v2 类型化子状态；阶段转移图数据化，`_phase_rank` 退役。
- 验收：行为基线全绿；处理器级单测覆盖每个短路分支；双引擎行为差分测试（同轨迹输入两策略的患者可见输出一致率 100%，规划选题差异除外并单独记录）；`server.py` 零改动通过全部现有服务端测试。
- 回滚：保留旧 `_submit` 于开关后一个版本周期，基线异常即切回。

### 阶段 3 · 推理核与语义层增强（工作量 L）
- 改动：假设工作区 + 更新协议 + 校验器；`DifferentialPlanner` 与选题打分；分诊第三层推理复核；`AssertionMap` 模型辅助实现（可选开关）；OSCE 病例集 ≥ 100 例并转发布硬门。
- 验收：5.1 中阶段三指标（Top-3 命中、弃权恰当率）达标；假设更新提议的校验拒绝率与原因分布可审计；影子 + 灰度按 5.4 完成。
- 回滚：Planner 策略开关切回 `RulePlanner`；工作区只读保留供复核。

### 阶段 4 · 纵向闭环与飞轮常态化（工作量 M）
- 改动：随访登记与结局标签（`patient_records` 扩展）；复核队列优先级；语料增量流水线与双周增量报告模板。
- 验收：一条完整的"问诊 → 随访 → 结局 → 标注 → 语料增量 → 评测报告"链路在测试环境跑通；复核队列能按三类分歧自动排队。

## 8. 风险登记册

| 风险 | 影响 | 缓解 |
|---|---|---|
| 红旗语料覆盖不足，召回率虚高 | 上线后真实说法漏检 | 变体生成 + 分歧挖掘 + 结局回流三路扩样；发布门只认 approved 样本；对未覆盖红旗显式标注"未评测"而非默认安全 |
| 语义/模型层不稳定导致分诊抖动 | 同一说法不同轮次结论不同 | 三层只许上调；结论随 TurnContext 冻结；模型输出必须过 schema 与证据子串校验 |
| 推理核给出错误鉴别方向 | 选题被带偏、问诊冗长 | 打分中红旗覆盖权重最高且独立于假设；停止/弃权规则为确定性代码；工作区只供复核端，患者侧不呈现诊断倾向 |
| 重构破坏既有问诊行为 | 更正、对象隔离等边缘功能回归 | 行为基线硬门 + 双引擎差分 + 每阶段可回滚开关 |
| 评测被"刷分"（针对语料过拟合） | 指标好看但真实质量不升 | 语料分开发集/留出集，留出集不参与调参；模拟患者与 OSCE 病例定期换新；分歧样本持续回流 |
| 临床标注供给不足 | 阶段三/四停滞 | 先用工程语料推进阶段 0–2（不依赖临床签署的部分），OSCE 病例允许小批量滚动扩充；文档明确标注哪些结论尚无临床证据 |
| 患者数据合规（事件日志含健康信息） | 上线合规风险 | 沿用现有文档的诚实边界：当前 JSONL 事件仅限研究原型；生产化前须另行完成加密、授权、留存与删除方案（不在本设计范围，上线前置条件） |

## 附录 B · 术语

- **红旗（red flag）**：提示可能存在急危重症、必须优先排除或立即升级处理的症状/体征/组合条件。
- **鉴别诊断假设空间**：系统内部维护的候选疾病集合及各自证据状态，仅供推理与医生复核，不向患者呈现为诊断结论。
- **弃权（abstain）**：系统判断信息不足或风险不可排除时，停止给出倾向性内容，转入固定升级话术与面诊建议。
- **影子模式**：新组件与旧组件并行计算但不影响患者可见输出，仅记录分歧用于评估。
- **行为基线**：以患者可见行为为断言对象的轨迹用例集，用于证明改造未破坏内核契约。
