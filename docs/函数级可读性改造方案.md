# 函数级可读性改造方案

> 状态：**待审查**。本文只是方案，没有动任何代码。
> 范围：`src/medagent` 中 49 个超过 100 行的函数，重点是最重的 8 个。
> 前提：组织层改造已完成——包分组、依赖方向、命名、公开面、测试目录都已固化并有门禁守着
> （见 [架构分层规则](架构分层规则.md)、[代码与命名规范](代码与命名规范.md)、[测试套件](../tests/README.md)）。

---

## 0. 为什么不动 "再分一次模块"

这件事做过，也有证据说明不该重做：

| 层面 | 现状 | 由谁守着 |
|---|---|---|
| 包分组 | 168 个模块，7 个内核包 + 7 个功能包 | `import_rules.py`，0 循环 |
| 依赖方向 | 四层，跨层导入为 0（含延迟导入） | `import_rules.py` R1–R6 |
| 文件命名 | 五种扩展名，语义名 | `naming.py` R1–R4 |
| 公开面 | 每个包 `__all__` 是字面量 | `tests/architecture/test_package_surfaces.py` |
| 导入 | 全仓 0 处 `import *` | `ruff` F403，无一处 `noqa` |
| 测试 | 161 个文件，按被测包分 13 个目录 | `naming.py` R4 |

**所以"读不懂"不在这几层。** 它在函数内部。实测：

```
1218 个函数，中位数 15 行 / 3 个分支   ← 大部分代码是正常的
49 个超过 100 行                        ← 占全部函数体代码的 24%
最大的 20 个占 13%，分布在 16 个文件
```

不是"到处都乱"，是**少数几个黑箱**。而这几个恰好是任何人都要读的地方。

## 1. 判定标准

改完要能验收，否则半年后漂回去。四条硬指标：

| 指标 | 上限 | 现状 | 处理 |
|---|---|---|---|
| 单函数行数 | 60 | 120 个超出，49 个 >100 | 基线冻结，只许减少 |
| 单函数分支数 | 20 | 38 个超出 | 同上 |
| 两项并集 | — | **59 个函数超标**（其中 28 个既长又绕） | 这就是基线要冻结的条数 |
| 单函数出口数 | 15 | `_submit` 30 个 | 拆到"一个阶段一次返回" |
| 模块入口 | docstring 写明"守什么规矩 + 从哪读起" | 质量高但入口不明 | 每个目标模块补 3 行 |

**为什么是"基线冻结"而不是"一次改完"**：49 个函数一次性重写等于重写半个后端，而唯一的护栏是测试。
冻结的含义是——不许新增超标函数，超标的只能一个个减少。这把"可读性"从一个愿望变成一个单调下降的数字。

## 2. Phase 0：先把尺子立起来

**先做这个，不做它后面的改动都会被稀释。**

新增 `scripts/lint/function_size.py`，与 `module_size.py` 同构：

- 扫描 `src/medagent/**/*.py`，按 AST 取每个函数的行数与分支数
- `BASELINE` 记录当前超标的 **59 个**函数（按 `模块::函数名` 作键；49 个超行数、38 个超分支，其中 28 个两项都超）
- 新增超标 → 失败；基线里的函数变短 → 提示删基线项；基线里的函数被删 → 提示
- 接入 `.github/workflows/main-quality.yml` 的 `Enforce module-size ceiling` 旁边

验证方式与现有门禁一致：`tests/architecture/` 里给脚本本身写 4 个用例（新增超标被拒、基线放行、
基线收敛后提示、改名后被当成新函数）。

复杂度：低。风险：无（只读代码，不改代码）。

## 3. Phase 1：`consultation/agent/submit.py::_submit`

**388 行 / 78 分支 / 30 个出口。用户说一句话进系统的唯一入口，任何人读这个项目都从这里开始。**

### 3.1 现状：它其实是一条直线

```
22   2行  if 紧急求助 → return
24   7行  if 过期动作 → raise
31   5行  text = 重试文本 or 用户输入
36   8行  if 自适应答案：改写 text
39   3行  if 位置文本：改写 text
42  10行  if 非危险文本：准备位置 + 5 个 check_*_action
52  33行 记录本轮（事件 + 转写 + 捕获担忧）
87   8行  risk = 分诊
95   4行  if 确认紧急澄清 → return
99  51行  if 否认紧急澄清 → 记录否认标签
164 37行  if 紧急 → 四分支澄清动作 → return
204  5行  if 位置修订 → return
209  6行  if 已结束 → return
215  8行  if 紧急且有挂起工作 → 拦截
223  3行  if 主体控制 → return
226 13行  if 准备好的位置 → 完成/记录 → return 或 _run
239  5行  if 任务对话动作 → return 或 _run
244 17行  if 计算补充 / 重试 → return
257  4行  清除反馈标记
265 12行  if 摘要确认 → return
277 21行  if 观察动作 → return 或 _run
298 10行  if 计算动作 → return
308  1行  对齐任务请求
309 73行  if 紧急初筛回答 → 记录事实 → 四分支澄清 → return
382  7行  if 摘要确认（与 265 行重复）
389 18行  if 活动任务 → 记录/挂起 → 紧急拦截
407  2行  pending_input + _run
```

无 `continue`、无 `break`、无内嵌函数，30 个 `return` 里 20 个是 `self._deliver(...)`。
**结论：这是最容易拆、也最该先拆的一个。** 它没有控制流陷阱，只有长度。

### 3.2 目标骨架

顶层读起来应该是五个阶段，每个阶段一次返回：

```python
def _submit(self, state: CaseState, user_input: UserInput) -> AgentReply:
    if user_input.choice_value == "request_emergency_help":
        return self._requested_emergency_help(state, user_input.text)

    turn = self._prepare_turn(state, user_input)          # 文本定稿 + 结构化输入
    turn_id = self._record_user_turn(state, turn)         # 事件 + 转写 + 担忧捕获
    risk = self._assess_turn_risk(state, turn)            # 分诊，含已走紧急通道的延续

    reply = self._emergency_turn(state, turn, risk, turn_id)
    if reply is not None:
        return self._deliver(state, reply, turn_id)

    reply = self._control_turn(state, turn, user_input, turn_id)
    if reply is not None:
        return self._deliver(state, reply, turn_id)

    reply = self._pending_work_turn(state, turn, user_input, turn_id)
    if reply is not None:
        return self._deliver(state, reply, turn_id)

    reply = self._answer_turn(state, turn, user_input, turn_id)
    if reply is not None:
        return self._deliver(state, reply, turn_id)

    state.pending_input = turn.text
    return self._run(state, turn.text, turn_id)
```

约 35 行。**"一次 turn 经过哪五关"从函数体第一屏就能看出来**，这是现在完全做不到的。

### 3.3 五个阶段与八个提取单元

| 新函数 | 源行 | 职责 | 预计 |
|---|---|---|---|
| `_prepare_turn` | 24–51 | 过期动作校验、重试文本、自适应答案、位置输入覆盖、五类控制动作的前置检查；返回一个小结构（text / adaptive / location） | ~45 行 |
| `_record_user_turn` | 52–84 | 写 `turn.user_message` 事件、转写、`_capture_worry`；返回 `turn_id` | ~30 行 |
| `_assess_turn_risk` | 86–94 | 分诊 + `closed_reason == "emergency_route"` 的延续 | ~10 行 |
| `_emergency_turn` | 95–200 | 澄清的确认/否认/四分支动作。**内含两个可再拆的单元**（见 3.4） | ~55 行（拆后 25） |
| `_control_turn` | 204–247 | 位置修订、已结束、紧急挂起工作拦截、主体控制、位置补全、任务对话 | ~45 行 |
| `_pending_work_turn` | 248–307 | 计算补充、两种重试、清反馈标记、摘要确认、观察动作、计算动作 | ~55 行 |
| `_answer_turn` | 309–406 | 紧急初筛回答（含事实记录）、摘要确认、活动任务 | ~75 行（拆后 40） |
| `_apply_emergency_denial` | 99–149 | 50 行的否认标签记录，纯数据整理 | ~40 行 |

拆到这一层，`_submit` 38 行，最大的子函数 75 行，全部低于 100。第二步再把 `_answer_turn`
内部的"紧急初筛回答"（73 行）单独提出来，就到 60 行以内了。

### 3.4 顺带消掉两处重复（这是拆分真正的红利）

**重复一：紧急澄清的 action→reply 映射写了三遍。**

| 位置 | 上下文 |
|---|---|
| `submit.py:164–200` | `_submit` 里，`risk.level == EMERGENCY` |
| `submit.py:345–375` | `_submit` 里，紧急初筛回答落库之后重新分诊 |
| `submit.py:491–518` | `correct_fact`，更正之后重新分诊 |

三处结构相同：`clarify` 且已否认过 → 降级；`clarify` → 提问；`confirmed` → 带澄清的紧急回复；
其余 → 紧急回复。差别只在用 `risk.triggers` 还是 `state.risk.triggers`。

抽成 `_emergency_clarification_dispatch(state, triggers, text, turn_id) -> Optional[AgentReply]`，
三处各留一行。**这一步会让 diff 变大（三处都动），但它是把"同一套临床判断"从三份变成一份**——
三份里只要有一份被改漏，紧急路径就会出现不一致的行为，而这是分叉最不该出现的地方。

**重复二：摘要确认判断写了两次**（`265–276` 与 `382–388`），后者少了两个 feedback 条件。
抽成 `_is_summary_confirmation(state, user_input, text)` + `_confirmed_summary_reply(...)`。

> 需要你决定：是否接受在 Phase 1 里顺手消重复（3.4），还是先只搬不改、下一轮再消（见第 9 节问题 3）。

### 3.5 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **`state` 是可变对象，写入顺序即语义** | 例如分诊必须在记录事实之后、担忧捕获必须在转写之后；提取函数改变顺序会静默改变临床行为 | 每个提取单元保持内部行序不变；只在单元边界切，不在单元内部重排 |
| **30 个出口合并成 5 个** | 现在每个分支自己 `return self._deliver(...)`；改成"返回 `Optional[AgentReply]`，顶层统一 deliver" | `_deliver` 除了返回还把回复存进 `_latest_replies`，需确认在阶段之间没有依赖它的副作用；逐个分支核对，不靠约定 |
| **`_prepare_turn` 里五类 `check_*_action` 是副作用而非返回值** | 它们修改 state，必须仍在这一步执行 | 保留在 `_prepare_turn` 内部，只为它写一个"这五个必须在记录本轮之前跑完"的注释 |
| **测试是按行为写的，不是按函数** | 覆盖 24 个 `tests/consultation/` 文件，拆函数理论上不改行为 | 覆盖率不足的函数在动之前先补测试，见 3.6 |

### 3.6 验证协议

```bash
# 0. 动之前先量：没有覆盖率的函数不拆
PYTHONPATH=src python3 -m coverage run --source=src/medagent/consultation -m pytest tests/consultation -q
python3 -m coverage report --include='*agent/submit*' -m

# 1. 每提取一个函数
PYTHONPATH=src python3 -m pytest tests/consultation -q

# 2. 五个阶段全部提取完
PYTHONPATH=src python3 -m pytest tests/ -q        # 基线：2006 passed / 71 skipped / 11958 subtests
python3 scripts/lint/function_size.py             # 基线里的 _submit 应可以划掉

# 3. 提交前
python3 scripts/lint/naming.py && python3 -m ruff check src tests scripts
```

判定：**subtests 数量必须仍是 11958**。这个数字比 passed 更敏感——它把每个参数的组合都算进去了，
少一个说明有分支没被走到。

## 4. Phase 2：`consultation/agent/run.py::_run`

**400 行 / 67 分支。骨架只有 13 条语句，其中一条是 341 行的 `for step in range(6)`。**

### 4.1 与 `_submit` 的关键差别

```
_submit: 0 个 continue、0 个 break、30 个 return   → 纯直线分派，可整段提取
_run:    1 个 continue、1 个 break、12 个 return   → 循环体不能整段搬进函数
```

`continue` 出现在"可修复的决策信封错误"分支（`L104–124`）：模型的输出格式错，把错误作为
tool_result 塞回同一轮，再试一次。`break` 在循环出口。这两个控制流跨越了函数边界，
**所以这一层的拆法必须先定一个"步骤结果"契约**，不能照搬 Phase 1。

### 4.2 可拆 / 不可拆

| 区块 | 源行 | 能否独立成函数 | 原因 |
|---|---|---|---|
| 决策调用 + 异常修复 | 76–157 | **否** | 含 `continue`（修复重试）和 `return`（中断/服务错误） |
| `record_facts` 的写入配额与拒绝键维护 | 158–213 | 是 | 纯记账，返回 `(writes, rejected_keys, goal_answered)` |
| 目标槽被担忧句占用时的分流 | 214–260 | 是 | 独立判断，只读 state |
| 工具结果事件与后续分派 | 261–411 | 部分 | 需先确认其中是否还有 `break` |

### 4.3 拆法：用一个显式的步骤结果代替控制流

```python
class _Step(Enum):
    PROCEED = auto()   # 继续下一步
    REPAIR = auto()    # 塞回 tool_result，continue
    ABORT = auto()     # 终止本轮，return 已交付的回复
```

循环体变成：

```python
outcome = self._take_step(state, turn, command, turn_id, messages, rejected_keys, writes)
if outcome is _Step.REPAIR:
    continue
if outcome is _Step.ABORT:
    return self._latest_replies[state.session_id]
```

复杂度：**高**。这是全仓风险最高的一处改动——它包着模型循环、取消语义、写入配额三条不变量，
而 `tests/execution*` 那 29 个文件只覆盖沙箱侧，模型循环的行为主要靠 `tests/consultation/` 的间接断言。

**建议：放在 Phase 1 之后做，先用手感验证 Phase 1 的验证协议是否够用。**

### 4.4 另一种更保守的选项

只拆 4.2 表格里明确"是"的两块（记账 + 担忧分流），不动控制流，`_run` 从 400 行降到约 300 行。
收益不大，但风险接近零。**如果 Phase 1 的收益已经够，就停在这里。**

## 7. 明确不做，以及什么条件下再做

| 不做的事 | 理由 | 重启条件 |
|---|---|---|
| **按业务能力重聚合模块**（把"用药提醒"从 dialogue / reports / consultation 三处合到一起） | 动模块边界的代价远高于拆函数；且现有分层是安全相关的（内核不依赖功能包） | 出现 ≥3 次"为一个改动翻 5 个包"的实例，再立项 |

| **`_preamble.py` 改名** | 6 个包、约 40 个 import 点；名实不符是真的，但它与函数改造正交 | 单独一轮，不与本方案混做 |
| **给每个函数补 docstring** | 长函数的问题不是没文档，是没有形状 | 拆完顺手补，不单独做 |

## 9. 需要你拍板的五件事

1. **函数行数上限取 60 还是 80？** 60 更严格，但 31–60 桶里现有 213 个函数，60 会在边界上晃；
   80 更宽松，可以先立住。我倾向 **60**，配基线冻结，不会一步到位。
2. **是否同意 Phase 1 顺手消重复（3.4）？** 会让 diff 从"移动代码"变成"移动 + 合并"，
   但紧急澄清的三份映射是真实隐患。我倾向**做**，且单独一个提交、单独审查。
3. **`_run` 拆到 `_Step` 枚举，还是只拆不涉控制流的两块？** 前者收益大风险高，后者安全但收益小。
   我倾向**先做后者**，把枚举留到有真实需求时。
4. **是否引入 `function_size.py` 门禁？** 它会让"临时写长一点"变成 CI 红。
   我倾向**引入**，否则本轮成果会在半年内被新增函数稀释。
5. **Phase 3/4 要不要现在排期？** 我的建议是**不排**——先做完 Phase 1，用一次真实的体验判断
   "读得懂"到底改善了没有，再决定要不要继续投。

```
chore(lint): bound function size, with today's 87 outliers frozen
```
