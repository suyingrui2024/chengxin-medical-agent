## 2. 排序调用点全图

### 2.1 调用关系（实测）

```
用户输入 → ConsultationEngine._h_planning (consultation.py:1667)
        → self.planner.plan(state)
            ├─ 默认：DifferentialPlanner.plan (reasoning.py:377 起)
            │     （MEDAGENT_PLANNER=rule 时才换成 RulePlanner）
            └─ 回滚：RulePlanner.plan (planner.py:25)
                  → ConsultationEngine._plan_next (consultation.py:1869)

自适应引擎（AdaptiveConsultationEngine，agent.py:234，继承 ConsultationEngine）：
  模型提议 ask_question → agent.py:2474 起的假设排序检查
        → ranker.choose(state, candidates)   ← 这里的 ranker 同样是 HypothesisRanker
  模型提议 ask_patient → validate_adaptive_question (adaptive_questions.py:86)
        → 只校验问题合法性（主题已注册、选项、禁令短语），不参与排序
```

引擎构造（`runtime.py:55`）：两个引擎都注入 `ranker=HypothesisRanker()`。
但注意：**ranker 对象的存在不等于 ranker 被使用**——默认 planner 路径下它
全程闲置（§2.4）。

### 2.2 各排序点的职责与现状差异

#### (a) `RulePlanner`（`planner.py:25`，34 行文件）

- 职责：仅转发，`plan(state)` → `engine._plan_next(state)`。本身无排序逻辑。
- 现状：它是“历史行为”的别名，不是独立策略。统一接口后它应退化为
  “目录顺序策略”的显式命名，而不是继续伪装成一个 planner。

#### (b) `ConsultationEngine._plan_next`（`consultation.py:1869`）

分三步，顺序不可打乱：

1. **过滤**（与 DifferentialPlanner 逐字相同）：`fact_key` 未记录
   + `question_applies_in_state` + `question_fact_gates_pass`。
2. **分阶段**：有 blocking 候选时取 `planning_rank` 最小阶段（`phase_graph.py:48`，
   `OPENING 0 / EMERGENCY_SCREEN 1 / HISTORY 2 / BACKGROUND 3`，其余阶段默认 9）；
   同阶段集合记为 `same_phase`；若同阶段首题是 `BACKGROUND`，先试
   `_offer_task`，且返回时包一层 `_attach_suspend_cap_notice`。
3. **选一**：`selected_id = self.ranker.choose(state, same_phase)`；
   若 ranker 返回的 id 不在 `same_phase` 内，回落到 `same_phase[0]`
   （fail-safe 回落，统一接口必须保留，不得改成抛错或返回 None）。
   无 blocking 候选时：先 `_offer_task`（同样包 suspend-cap 提示），再走
   G-12(d) 关闭前鉴别点 `_undetermined_close_discriminator`（`consultation.py:1950` 起，
   固定题序 `emergency_screen → gi_details → trajectory → dizzy_details`，
   再加一次性 re-ask），最后 `_finish`。

关键点：`_plan_next` **不计分**。它把“同阶段内排谁先”完全交给 ranker，
自己只负责过滤 + 分阶段 + 回落。

#### (c) `HypothesisRanker`（`hypothesis_ranking.py:139`，模块自述见文件头）

- 契约（模块头注释逐字承诺，本次重整须原样保留）：
  “只对已过滤的 `same_phase` 候选集排序；不做过滤、不改阶段顺序、不增阶段。”
- `order(state, candidates) -> List[str]`（`hypothesis_ranking.py:300` 起）：
  - 非 HISTORY 阶段：**原样返回目录顺序**，不重排。
  - 仅 HISTORY 重排，分组固定：(0) 通路外警告题（P3 hook，见下）→
    (1) 风险为 URGENT/EMERGENCY 时缺失的 `URGENT_MINIMUM_FACTS`（按该表顺序）→
    (2) 深挖组 = `{onset, trajectory, severity}` + `applies_when` 主诉词命中
    的细节题（组内按 `q_score`）→ (3) `associated_symptoms` →
    (4) 其余（按 `q_score`）。
  - `q_score = 2 × 是否可证伪 + top-5 假设中列为 discriminating 的次数`；
    可证伪 = `fact_key` 出现在 top-3 假设的 refute 条件里，或题 id 出现在
    top-3 之外假设的 `discriminating_questions` 里；平局按 `questions.json`
    目录顺序，绝不按传入顺序。
  - 假设分：`acute(红旗 3 / 其他 1) × PRIOR_RANK(high 3 / medium 2 / low 1)
    × season_w × age_w × evidence(max(0, 1 + 0.5×support − 1.0×refute))`；
    **季节 / 年组权重表目前全为 1.0 平权，待临床签核**——统一接口不得
    “顺手”填权重，那是临床签核项，不是重构项。
  - 通路外 hook：主诉不匹配任何通路时查 `out_of_pathway.warning_questions`，
    但该函数返回的 dict 目前**不带题 id**（模块头注释自承的集成点），故
    `_warning_ids` 实际常为空。统一接口不得“修复”这个 hook 的语义，
    只原样搬运；hook 语义变更记为跟进项（§10）。
- `choose(state, candidates)` = `order(...)[0]`，空集返回 None。

#### (d) `DifferentialPlanner`（`reasoning.py:377`）

- 与 `_plan_next` 共享过滤与分阶段（代码逐字平行：同样的三条件过滤、
  同样的 `planning_rank` 最小阶段、同样的 `same_phase`、同样的
  BACKGROUND 先 `_offer_task`），但有三处**行为差异**，搬移时必须逐项保真：
  1. **BACKGROUND 的 `_offer_task` 返回不包 `_attach_suspend_cap_notice`**，
     而 `_plan_next` 包。两处不得“统一”成一种——那会改变一方的提示行为。
  2. **选一规则完全不同**：`max(same_phase, key=(score, -index))`，
     其中 `score = 3.0×红旗 + 2.0×鉴别（≥2 个 active 假设共享，或
     potential_counts ≥ 2）+ 1.0×W_REQUIRED + 0.5×新鲜度`（权重见
     `reasoning.py:417` 起注释，v1 无负担项——曾有个未接线的 W_BURDEN
     常量已被删，勿复活）。
     平局规则是 `-same_phase.index(q)`（即**先出现的胜**），与
     HypothesisRanker 的“目录顺序平局”在输入顺序即目录顺序时等价，
     但语义来源不同，搬移时须保留 max + 负索引的原表达式，不得改写为
     sort 取首（sort 的稳定性与 max 的平局语义在实现上可等价，但
     审计时必须用 §9 的对照证明，不允许凭直觉替换）。
  3. **无 blocking 候选后的路径完全不同**：不走 G-12(d) 鉴别点，
     而是走红旗假设“卡住 3 轮 + 仍 active”的 abstention 分支
     （URGENT → `_urgent_or_defer` / ROUTINE 或已 defer → `_finish` /
     其他 → `_urgent`），最后 `_finish`。
     注意：G-12(d) 是 `_plan_next` 独有的关闭前追问，DifferentialPlanner
     路径下**不存在**——这是 planner 差异，不是排序差异，绝不能在
     统一排序接口里“补齐”。
- 还负责 workspace 刷新与校验（`_refresh_workspace`、
  `_potential_discrimination`、事件 `reasoning.proposal_rejected` /
  `reasoning.workspace_updated`）：这些属于推理层，不属于排序层，
  **不得**随排序抽离一并搬走。

#### (e) 自适应检查（`agent.py:2474` 起，ask_question 工具分支）

- 检查而非决策：模型提议某题时，用 `ranker.choose(state, candidates)`
  算出“应先问谁”，提议不一致则抛 `ProposalError`（模型自纠循环再提议）。
- 与 `_plan_next` 的四处差异，统一接口必须原样保留：
  1. 候选集是 `_candidate_questions`（`agent.py:1361`）的**全量过滤结果，
     未按阶段切 same_phase**——把检查改成 same_phase 会改变自适应行为，
     禁止。
  2. 豁免：澄清轮（`active_question_is_clarification`）、当前题的跟进、
     待处理急症澄清（`_emergency_clarification_pending` 非空）时不检查。
  3. 直通：`pick` 或提议题任一不在候选集内时**放行**，不抛错
     （防模型陷入无法退出的提议循环）。
  4. 候选集本身与 `_plan_next` 的过滤在措辞上平行（未记录 +
     `question_applies_in_state` + fact gates，`agent.py` 侧走
     `_fact_gates_pass`），但函数名与落点不同——统一时只统一“过滤谓词”
     的语义说明，不强行合并两个函数，除非对照证明逐字等价。

#### (f) 自适应问题校验（`adaptive_questions.py:validate_adaptive_question`）

- 不参与排序：只校验模型自写问题的结构（必填字段、主题在题库 fact_key
  注册集内、选项 ≤8、禁令短语等）。本次重整**不碰**它；
  把它列入本节仅为防止实施时误把它当成“排序逻辑”一并抽走。

### 2.3 现状差异总表（实施对照用）

| 维度 | `_plan_next` + ranker | DifferentialPlanner | 自适应检查 |
|---|---|---|---|
| 过滤 | 未记录 + applies + fact gates | 同左（逐字平行） | 同左（全量，未切阶段） |
| 分阶段 | `planning_rank` 最小阶段 | 同左 | 不分阶段 |
| 同阶段内排序 | HypothesisRanker：仅 HISTORY 重排分组 + q_score，余者目录序 | 自有 score（3.0/2.0/1.0/0.5）+ max 负索引平局 | 复用 ranker.choose 作“应先问谁” |
| ranker 是否参与 | 是 | **否（§2.4）** | 是 |
| BACKGROUND offer 包装 | 包 suspend-cap 提示 | 不包 | 不适用 |
| 无 blocking 后 | G-12(d) 鉴别点 → `_finish` | 红旗卡住 abstention → `_finish`/`_urgent` | 不适用（检查只否决提议） |
| 回落 | ranker id 失配 → `same_phase[0]` | max 恒有解，无回落 | pick/提议不在候选集 → 放行 |

### 2.4 必须标出的事实：DifferentialPlanner 默认路径目前未被 ranker 覆盖

- 实测：`reasoning.py` 全文**零处**出现 `ranker` / `HypothesisRanker`
  / `self.ranker`；`DifferentialPlanner.plan` 从头到尾只用自己的
  `score()` + `max()`，从未调用 `engine.ranker`。
- 而引擎默认 planner 正是 DifferentialPlanner
  （`consultation.py:352` 起注释：2026-10-23 A/B 评估后晋升为默认，
  `MEDAGENT_PLANNER=rule` 为回滚）。
- 推论：**当前线上默认题序 = DifferentialPlanner 计分，与 HypothesisRanker
  的 HISTORY 分组 + q_score 是两套互不相干的排序**；只有在回滚
  `MEDAGENT_PLANNER=rule` 时，ranker 才接管同阶段排序。
- 对统一接口的硬性要求（总协调须在实施包中逐字写入）：
  1. 统一接口必须是**策略分发 + 共享脚手架**（过滤谓词说明、分阶段
     helper、回落约定），而不是**单一计分函数**。把 DifferentialPlanner
     的计分强行并入 ranker 的 q_score，或把 ranker 的 HISTORY 分组
     强加给默认路径，都会改变默认题序——**禁止**。
  2. 接口后默认路径仍走 DifferentialPlanner 计分原表达式，行为上
     与接口前逐轮一致（§9 对照法验证）。
  3. 两套排序的统一（是否最终收敛为一套计分）记为**跟进项**，须另立
     评估报告（沿用 `scripts/evaluation/medical/evaluate_planner_ab.py`
     的 A/B 口径）并经用户拍板后才能做；本次重整不做、不暗示、不预埋
     开关改变默认行为。

## 3. 收尾层抽离

### 3.1 choke 点现状（`consultation.py:_record_reply`，3,244 行起）

`_record_reply` 是双引擎共享的唯一 choke 点，现有顺序（实施时不得重排）：

1. `_apply_bridging`、`_apply_group_bridge`（每轮装饰，非收尾，见 §3.3）；
2. publication gate 校验（不通过且为 EMERGENCY 时先关会话，再 fallback 改写 reply）；
3. 事件 + `commit_phase`；**仅当本轮真正发生 transition 且 reply.phase == CLOSED 时**，
   才依次做：`_attach_conclusion`（仅 `closed_reason` 为
   `confirmed_by_user` / `urgent_route` 且 gate 通过时）→ `_speak_close_line`
   → urgent  close 的 sheet 附加（§3.2）→ P3 scope note（同上两个
   closed_reason 内）。
   注意：已关闭会话的 guard reply（无 transition）不重复说处置、不重复
   scope note——这是防重复渲染的关键条件，抽离时必须原样保留调用条件，
   不得把收尾 append 提升到 transition 判断之外。
4. 其余：subject 清理、calculation/observation 投影、revision 自增、
   `turn.agent_reply` 事件、transcript、最新 reply 快照、持久化。
   这些**不属于收尾层**，留在 `_record_reply` 内。

## 4. 结论渲染单源：三处门控现状与 M2 前科

### 4.1 唯一事实来源：composer（`conclusion.py`）

- composer **始终计算**方向与科室（`compose_conclusion` 约 1,829 行起）：
  方向经 `_select_directions` 选出，科室经 `_department_hint`

### 4.3 M2 前科：打印绕过门控是怎么发生的

- 据《阿福对标改造设计文档》P3/P4 段记载：独立监督一轮拦下
  M1（解读注释不可见）与 **M2（打印 narrative.reasoning 绕过 shadow 门控）**
  并已修完。M2 的机制正是 §4.2 的模式：打印模块最初直接取
  narrative.reasoning 输出，而 reasoning 逐条引用方向标签
  （`conclusion._narrative_reasoning`），等于把 shadow 方向经由“原理”段落
  泄漏到了打印/导出件上；修复是在打印模块内补了
  `directions_visible === true` 门控，并在 `app.js` 抄 narrative 时补了
  第二道门（“双重保险”）。
- 教训（写入契约，而非只记在文档里）：
  1. **凡含方向标签的派生文本（reasoning、support_quotes、against_note）
     都与方向同门**，不能只 gate 方向列表本身。单源契约必须把“哪些字段
     与方向同门、哪些与科室同门”列成表（§4.4），而不是让每个渲染器
     各自领悟。
  2. “上游已剥离，所以下游不用 gate”是**不成立**的防御：上游剥离是
     端点实现细节，打印模块的输入契约一旦换成 live sheet（`openHandoff`
     的 narrative 正是从 live sheet 抄的），剥离假设即失效。
  3. M2 修复提交的逐 commit 定位本次审计未做（只核对了现状代码与
     对标文档记载一致），记为**待核实**：实施前由实施包核对 M2 修复
     diff，确认 §4.4 的字段表覆盖了当时的泄漏面。

### 4.4 单源契约的具体形态（目标）

**Composer 输出（唯一事实源，`conclusion.py` 不变其计算，只冻结契约）：**

```python
sheet = {
    "directions": [...],            # 恒算、恒在；shadow 下仍在 sheet 内，不删
    "directions_visible": bool,     # 唯一方向可见性事实
    "department_visible": bool,     # 唯一科室可见性事实
    "disposition": {
        "level": ..., "text": ..., "window_hours": ...,
        "department_hint": {...} | None,   # 恒算；可见性由 department_visible 定
    },
    "narrative": {
        "framing": ..., "severity": ...,    # 恒可见（不含方向）
        "reasoning": ...,                   # 与方向同门
    },
    # 其余字段（gaps / self_care / return_now_if / worry / goal_response /
    # outlook / follow_up / abstain_text）不走方向/科室门，恒可见。
}
```

**字段—门控归属表（渲染器照表执行，不得自行发挥）：**

| 字段 | 门 |
|---|---|
| `directions[]`（含 patient_label、support_quotes、against_note） | `directions_visible` |
| `narrative.reasoning` | `directions_visible`（与方向同门，因逐条含方向标签） |
| `disposition.department_hint` | `department_visible` |
| `narrative.framing`、`narrative.severity`、`disposition.text`、`gaps`、`self_care`、`return_now_if`、`worry`、`goal_response`、`outlook`、`follow_up` | 无门（恒可见；worry/goal 是患者自己的问题，见 §4.2） |

**渲染器消费规则（所有渲染器统一）：**

1. 只读 `directions_visible` / `department_visible` 两个 bool，不读
   环境变量、不推导、不回落（`app.js` 的“无 live sheet 时有方向即
   可见”回落分支**必须删除**，改为：无 live sheet 时以端点输出为准，
   端点输出无方向即不可见）。
2. 打印脚本 `handoff-print.js` 必须补上科室门：
   `department_hint` 仅当 `conclusion.department_visible === true`
   时输出；同时方向与 reasoning 保持现有的 `=== true` 严格判断。
   注意打印脚本的输入可能是端点输出（department_hint 已剥离）也可能
   是 live sheet 派生——两种输入下同一判断都必须成立，这正是“消费
   flag 而非信任上游剥离”的含义。
3. 交接端点 `handoff.py` 的职责收敛为**传输裁剪**（按 flag 决定是否
   携带方向/科室字段），且裁剪后**仍须保留两个 flag 字段本身**透传给
   下游（现状 `_conclusion_section` 未透传 flag——打印模块读
   `conclusion.directions_visible` 时依赖的是 `app.js` 事后补的 flag，
   不是端点给的；单源契约要求端点透传 flag，`app.js` 不再补 flag）。
   若端点保持“剥离即门”的 shape 契约（`directions: None`），则须在
   契约中写明：剥离是传输优化，不是第二道门；渲染器仍以 flag 为准，
   flag 缺失时按不可见处理（fail-closed），绝不按“有字段即可见”回落。
4. 前端结论卡 `structured-ui.js` 现状已符合消费规则，**只做搬移不改
   判定**（判定表达式原样保留，作为回归锚点）。
5. 新增渲染器（未来任何第四处）必须先在 §4.4 的字段表里登记门控，
   否则不得上线；测试须覆盖“shadow 下打印/导出/结论卡三处均无方向、
   无 reasoning、无科室”的组合断言（现状 `tests/ui/handoff-print.spec.mjs`
   覆盖打印，结论卡见 `conclusion-card.spec.mjs`，需核对三处是否同
   覆盖——**待核实**）。

## 5. canonical 在 web 层的全部用途

`canonical` 只有一个生产者、三个消费点（另有两处同名无关项，见表末）。
生产者：`presentation.py:91`，`reply_presentation` 在问题块里写

**canonical 门控应保留 / 放开的原则（写入新方案）：**

- **保留在“内容身份”判断上**：spec 标题 / 图标 / hint / cues /

  凡守卫的是**控件**（量表、选项组、输入框类型）一律改跟 `question_id`；
  凡守卫的是**文案资产**（标题、hint、cues）一律保留跟 canonical。

- **emergency 信号格不动**：`question_id === "emergency_screen" && spec`
  的双条件现状保留（信号格是题库资产，不是输入控件；且 emergency
  信号格的误显/漏显是安全相关，改动须另立安全评估，不在本轮）。
