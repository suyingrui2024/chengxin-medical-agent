# 执行效率与收尾问题分析

本记录来自 v0.10.2 固定公开 TEST 对照的已完成运行，是开发问题分析，不是新的效果证明。完整 24 次计划已结束；当轮执行源码、任务与原始判分保持冻结，不能把后续改进混入原实验。

已观察到两类独立问题。一类是修复遗漏相关操作：Sphinx 8627 产品第一次只给 `stringify` 增加内置类型映射，未修复 `restify`，独立验收两个指定测试仍失败。另一类是实现已正确但执行没有收尾：SymPy 21627 产品第一次通过独立 27 节点验收，轨迹中先有相关测试 `65 passed, 3 xfailed`，随后单独新回归 `2 passed`，再启动更大的额外套件，反复读取仍在运行的同一后台任务，最后用尽 20 次共享请求。官方 SDK 同题第一次也在正确修改后用尽额度。不能把这些不同原因都称作代码错误。

当时产品每次前台／后台输出等待最多 30 秒，之后回到模型决策。这有利于分段观察，但模型重复请求 `job_output` 会消耗模型额度。调用者要求等待 250000 或 280000 毫秒时，实际仍被截为 30000 毫秒；短等待策略与默认 SDK 不同。已有动态剩余额度提示和“必要检查通过后收尾”的系统指令仍不足以保证模型执行该策略。

后续改进应先依据完整轨迹确定范围，再建立独立实验，而不是增加更多泛化提示或只扩大额度。候选方向包括：

- 让长任务等待与模型决策分开：在同一次工具等待中持续更新界面状态，并保留立即停止入口；避免仅为“仍在运行”再次请求模型。实际停止、截止时间和工具取消必须单独实测。
- 预算将尽时提供明确的收尾机会，说明已完成、失败和未验证项；不能将预算耗尽改名为成功，也不能隐藏未完成的后台任务。
- 将相关路径检查与结果复核纳入任务计划，减少只改一个入口、忽略同类操作的修复。以代码与独立反例核对，不把模型自写的预期值当作正确性依据。
- 用独立行为审阅区分“检查器证实实现正确”“模型运行过相关测试”“模型正常收尾”。文件契约门并不自动覆盖所有行为要求。

验收需要在相同 20 请求／600 秒条件下观察改进，保留之前失败与成本，不通过增加额度使结果看似改善。若本组 TEST 的失败被用于修改产品，这组已成为本项目的开发证据；后续重测只能称已知任务回归，还需预先冻结新的独立样本检验推广效果。两次重复、六题及四仓库的范围不支持全面不劣于 DSH 或 Codex 的结论。

## 独立显式等待实验

候选位于 `.runtime/v0103-wait-experiment`，没有修改正在评测的正式源码。它保留前台 30 秒上限和后台默认 10 秒等待，仅把调用者明确要求的 `job_output(wait=true, timeout_ms=...)` 最大等待恢复为固定 SDK 支持的 600 秒；共享任务截止与取消仍由原控制器执行。配置检查和系统提示需同步反映该区别。

本机确定模型、真实 SDK 和同一 34 秒后台命令的检查中，旧策略第三次模型请求在 30.06 秒到达、任务仍在运行；候选第三次请求在 34.06 秒到达、实际产物已写入并收到结束输出。这里没有证明完成完整任务总请求数降低：旧策略仍可再请求一次等待。它只证明显式等待能够跨过旧上限而无需中途再次决策。

首轮新用例错误检查了包含历史命令的整段请求，完成标记因此被误读，已改为只看工具返回；早期失败保留。新用例还最初假定超时必须为 failed，候选曾据此修改状态，随后已有回归测试指出这与现有契约冲突。项目原契约为 `cancelled` 加 `time_budget_exhausted`；它不等于用户主动取消。已撤销候选状态改动，并按原契约重验。不得把新测试与既有契约冲突当作原版缺陷，也不能修改旧测试使候选通过。

上述实验仅证明等待机制；正式合入、完整回归和真实模型效果仍需后续完成。它不能代替固定公开任务对照或证明整体达到 DSH。

## v0.10.3 合入范围

显式后台等待已合入，前台 30 秒上限和默认等待保持不变。完整后端已实际验证 185 秒任务沿用同一进程，三次确定模型请求完成启动、一次显式等待和收尾；取消与截止时间检查通过。上述同请求数的机械控制组不能证明真实模型总体调用数下降，也没有重新运行这六个已知公开任务来声称泛化提升。原实验失败、原始 24 份候选和独立审计继续保留。


## 真实模型同预算等待策略对照（已完成）

2026 年 10 月 16 日启动独立诊断实验。因已知失败而选择 SymPy 21627 和 Sphinx 8627，每题两次重复、两条路径共八次运行；这些是开发任务，不是独立保留集。每次同一模型、同一任务原文与文件契约、同一准备源码、20 次模型请求和 600 秒，总上限 160 次。顺序种子 2026101603 决定首组顺序，随后在题目和重复间平衡两条路径的先后。

两条路径均使用当前 0.10.3 控制器与完整 SDK。控制组只将 `job_output` 显式上限还原为 30 秒，并同步对应系统说明；候选为 600 秒。其他集成文件逐字一致，Node 依赖共享同一锁定安装；不把控制组称作整个 0.10.2 产品，也没有本轮独立官方 SDK 臂。源码与评测器在首次调用前冻结。

独立验收恢复原测试、配置与依赖后应用候选实现，分别记录实现、文件契约与正常收尾。候选读取复用已验证的 no-follow 规则，保存修改字节、删除项和链接原文；运行结束并保存这些资料后只清理本次新建的工作副本。旧程序、旧归档及准备源码不删除。所有失败和请求账本保留，不以增加额度或换题获得通过。

入口为 `scripts/benchmarks/public/benchmark_wait_policy.py`；不带 `--live` 只输出计划且不读取密钥。原始报告为 `.runtime/evaluations/wait-policy-v0103/round1.json`，开始时已写入完整条件和冻结摘要。八次计划已经结束，实际 160 次请求。实现与文件约束均为两组各 4/4；正常收尾为 30 秒组 3/4、600 秒组 0/4，两组各消耗 80 次请求。因此本组没有证明真实调用数或完成表现改善，不能宣称整体达到 DSH。


另做统一补充审计，发现 600 秒组的两份新增回归测试失败：一份数学预期错误，一份使用当前版本不支持的 API 参数。原指定节点通过不能代表这些新增交付文件也正确。补充门在观察失败后建立，标为 post-hoc，原评分与候选不改；它没有改变本轮原联合完成数量。八份候选已按归档字节重建并逐节点重放一致，原始缺陷负对照被拒绝；新临时项目也成功从归档重建两个环境，128 个冻结文件一致。详细结果、边界和复现见 [本轮归档](evaluations/2026-10-16/v0.10.3-wait-ablation/README.md)。

下一阶段优先补强交付检查与预算内纠错：新增测试须实际执行、零用例不能视为通过、未执行项明确显示；在预算早期获得失败反馈，而不是将最后一次调用花在首次等待结果上。保留现有 600 秒显式能力的机械验证，不将其包装为已证明的智能效率提升。
